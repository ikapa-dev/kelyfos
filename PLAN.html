section 1

End goal & definition of done

Mission. Build the guest OS layer that every agent-sandbox platform treats as an afterthought: a tiny, immutable Linux image whose init system speaks MCP, with security policy and auditability baked into the image itself — self-hostable on any Linux/KVM box, portable across microVM runtimes.

The project is done (v1.0-worthy) when all of the following are true:

  • A fresh user goes from git clone to a working sandboxed agent command in under 5 minutes on a stock Linux/KVM machine.
  • kelyfos run --image dev --workspace . --allow github.com --secret GITHUB_TOKEN@github.com -- <agent cmd> works as advertised: the agent operates only through MCP tools on your project files, egress outside the allowlist fails, and the secret value never exists inside the guest.
  • Boot-to-ready ≤ 300 ms cold, ≤ 100 ms from snapshot; kelyfos fork -n 4 yields four divergent copies of a prepared environment.
  • Every session produces a complete, tamper-evident (hash-chained) audit log — live (kelyfos log --follow, kelyfos watch) and exportable as a standalone, verifiable HTML session report.
  • An E2B-compatible API shim passes an SDK smoke test, so existing code can point at a self-hosted kelyfos box.
  • Published as open source with a README, quickstart, and demo; John uses it for his own Claude Code runs (dogfooding).

Strategic intent: reputation, learning, and consulting leads first. The one commercial thread worth keeping alive is the EU-compliance / self-hosted angle (hardened, auditable images + support for European teams). Revenue is a bonus, not the goal.

section 2

What we are building

ComponentDescription
image/ A Buildroot pipeline producing two artifacts: a stripped vmlinux (virtio-only, no modules) and a read-only ext4 rootfs (target < 200 MB) with a tmpfs overlay for writes. Flavors: base, dev, later browser.
supervisor/ The novel software. One static Go binary running as PID 1 inside the guest: mounts, zombie reaping, and an MCP server over vsock exposing the machine as tools — exec, read_file, write_file, list_dir, upload/download. No SSH, no shell login, no cloud-init. The sandbox is a toolbox, not a computer.
host/ The kelyfos CLI (Go): assembles Firecracker config, boots/stops VMs, bridges MCP to stdio, runs the egress proxy (deny-all + domain allowlist), injects secrets at the proxy so credentials never enter the guest, packs and syncs --workspace directories, self-checks the environment (kelyfos doctor), and writes the flight recorder (append-only, hash-chained JSONL of every tool call and network attempt).
shim/ E2B-compatible REST subset (create sandbox / exec / files) so existing SDK users can point at a self-hosted kelyfos host. Adoption hack, phase 3.
snapshots First-class snapshot/restore/fork via Firecracker snapshots: clock resync, entropy, network re-init handled correctly so one prepared environment forks into N parallel branches.

Non-goals — hard boundaries

  • No new kernel. Stock Linux, custom config only.
  • No VMM. Firecracker (cloud-hypervisor later, maybe). We ship what boots inside it.
  • No orchestrator, no control plane, no hosted service, no web dashboard. Single-host CLI; monitoring is read-only viewers over the flight recorder (decision D7). Fleet management is someone else's product.
  • No GUI desktop / computer-use layer in v0.x. Headless browser flavor is the closest we get, and only in phase 4.
  • No Kubernetes integration in v0.x.
Scope discipline is the project's survival strategy. Every one of these non-goals has a funded startup already doing it. The guest image is the empty niche — stay in it.

section 3

Why this exists

The runtime layer is crowded (E2B, Daytona, Beam, Temps, PandaStack, Microsandbox, OpenComputer, Northflank, Modal…). All of them build control planes and boot a generic Ubuntu/Alpine rootfs inside. Nobody ships the guest itself as an opinionated, portable product: MCP-native init, deny-all egress, secrets kept outside the VM, audit-first design. The analogy is Talos Linux — Talos didn't compete with Kubernetes, it became the OS purpose-built to be run by it.

Differentiators, in priority order: (1) agent-native interface — the guest is a set of MCP tools, not a computer with a shell; (2) auditability — a replayable flight recorder nobody else offers out of the box; (3) self-hosted and EU-friendly — data residency is the one buying reason the US-hosted platforms cannot serve.

config KELYFOS_PHASE_1

Phase 1 — Minimal bootable guest (v0.1 · "it boots")

DONE

Goal: a self-built kernel + rootfs that boots under Firecracker and answers one command over vsock. Est. 3–4 weekends.

  • P1-0Spec before code — write docs/protocol.md covering: (a) Firecracker's hybrid vsock model — the guest speaks AF_VSOCK, but the host side is a dedicated Unix domain socket (this is not the Firecracker API socket, and no host vsock kernel module is involved): host-initiated connections open the vsock UDS and send CONNECT <port>\n, guest-initiated connections to host CID 2 port N land on <uds_path>_<port>; (b) project constants: vsock.guest_cid = 3 and the port assignments (exec, log, MCP channels); (c) the newline-delimited JSON frame schema for exec (request id, cmd, stdin, timeout; response chunks: stream, data, exit code); (d) MCP framing for phase 2: newline-delimited JSON-RPC per the MCP stdio transport spec — "Messages are delimited by newlines, and MUST NOT contain embedded newlines" (spec §Transports, all revisions incl. 2025-11-25); explicitly not LSP Content-Length framing — so the kelyfos mcp bridge is a pass-through. All later tasks implement this document.
  • P1-1Buildroot external tree parameterized by ARCH (aarch64 primary — the dev machine; x86_64 second): musl, BusyBox; make toolchain downloads and prepares Buildroot pinned to a release, defaulting ARCH to the build host.
  • P1-2Kernel config fragments per arch: virtio-blk, virtio-net, virtio-vsock, ext4, no loadable modules, no real-hardware drivers, quiet boot. aarch64 and x86_64 differ in console device and boot arguments — keep those bits in arch-specific fragments and verify each against the Firecracker docs. Artifact formats are strict: aarch64 must produce the uncompressed Image build target (not Image.gz); x86_64 must produce the uncompressed ELF vmlinux (Firecracker does not boot bzImage). The fragments must also state # CONFIG_MODULES is not set explicitly — "no loadable modules" is a config assertion, not a hope.
  • P1-3Guest init script: mount /proc, /sys, /dev, tmpfs overlay on a read-only root, then start a vsock listener stub.
  • P1-4make image outputs the kernel artifact (Image on aarch64, vmlinux on x86_64) + rootfs.ext4; rootfs < 200 MB.
  • P1-5kelyfos run (Go, in host/): write Firecracker config JSON, boot the VM, clean teardown on Ctrl-C.
  • P1-6kelyfos exec "<cmd>": newline-delimited JSON over Firecracker's vsock UDS → run in guest → return stdout, stderr, exit code.
  • P1-7Measure boot-to-ready (host timestamp → first vsock heartbeat). Record the number in the progress log. Target this phase: ≤ 500 ms.
  • P1-8Cross-arch gate: make image ARCH=x86_64 cross-builds cleanly on the aarch64 dev machine (build only — no local boot required). From this point it must keep passing on every commit; boot verification for x86_64 lands with CI in P3-6. Pulled forward so x86-specific breakage is caught in days, not weeks.

config KELYFOS_PHASE_2

Phase 2 — Agent-native supervisor (v0.2 · "a toolbox, not a computer")

DONE

Goal: the differentiating layer — MCP as the only interface, policy and audit built in. Est. 3–4 weekends.

  • P2-0Design gate before P2-5/P2-6 — HTTPS makes plain CONNECT tunneling incompatible with header injection, so choose the TLS strategy: (a) TLS-terminating proxy with a per-install kelyfos CA baked into the guest trust store (transparent injection, MITM within your own box), or (b) CONNECT-only tunnel plus a guest-side credential helper that fetches short-lived tokens from the supervisor (no MITM, needs tool cooperation). Prototype the riskiest part, record the choice as decision D6, then implement P2-5/P2-6 accordingly.
  • P2-1Supervisor as PID 1 (static Go binary): mounts, zombie reaping, clean shutdown on vsock command. Replaces the P1 init script.
  • P2-2MCP server over vsock with tools: exec (streaming stdout/stderr), read_file, write_file, list_dir, upload, download.
  • P2-3kelyfos mcp: stdio ⇄ vsock bridge so any MCP client (Claude Code first) can attach to a running sandbox.
  • P2-4Flight recorder: every tool call and result appended as JSONL on the host; kelyfos log [--follow] replays a session. Stable, versioned event schema documented in docs/events.md (command start / output / exit, file writes, egress allowed / blocked, secret use by name — never values). Each event embeds the hash of the previous event, making every session log a tamper-evident chain verifiable with kelyfos log --verify. The P3 viewers build on this contract; the schema is the product, viewers are replaceable.
  • P2-5Egress off by default (no NIC). --allow d1,d2 boots with a NIC: the CLI creates a per-VM TAP (ip tuntap add kelyfos<id> mode tap, /30 point-to-point addressing, no NAT and no IP forwarding — none is needed, because the proxy and DNS responder bind directly on the host's TAP address, so guest traffic terminates on the host and only the proxy process itself can reach the internet) and installs an nftables chain on it permitting only the host-side proxy port and DNS, dropping everything else; the guest gets HTTP_PROXY/HTTPS_PROXY pointing at the proxy (HTTP(S) CONNECT + DNS restricted to the allowlist). The exact nftables rule template is written into docs/networking.md as part of this task. Every attempt (allowed or blocked) is logged.
  • P2-6Secret injection: --secret NAME@domain — the proxy attaches the credential to matching requests; the value never appears in guest env, disk, or logs.
  • P2-7End-to-end dogfood: Claude Code attached via kelyfos mcp completes a small real task (clone a repo, edit, run tests) entirely inside the sandbox.

Acceptance test — recreate & verify

  1. kelyfos run --image base --allow github.com → sandbox up.
  2. Attach an MCP client via kelyfos mcp → tool list shows the six tools.
  3. Inside: exec "git clone https://github.com/octocat/Hello-World" → succeeds (allowlisted).
  4. Inside: exec "curl -m 5 https://example.com" → fails; the attempt appears as blocked in kelyfos log.

  7. kelyfos log --verify passes on the session; flipping one byte in the JSONL makes it fail.

config KELYFOS_PHASE_3

Phase 3 — Snapshots, flavors, compatibility (v0.3 · "fork it")

ACTIVE

Goal: the performance story, the daily-driver UX, and the adoption hack — then go public. Est. 5–7 weekends.

  • P3-1kelyfos snapshot save|restore via Firecracker snapshots. On resume the host sends a resync RPC over vsock — wall-clock timestamp plus fresh random bytes — and the supervisor applies them with clock_settime(CLOCK_REALTIME) and a write to /dev/urandom (ptp_kvm + chrony considered and rejected: too heavy for a BusyBox image). Target restore ≤ 100 ms.
  • P3-2kelyfos fork -n N: N restores from one snapshot, with the mechanism made explicit. The rootfs block device is opened read-only and shared by all forks — divergent writes already live in the in-guest tmpfs overlay, which is part of guest memory; each fork maps the memory snapshot file privately (MAP_PRIVATE), so the OS provides page-level copy-on-write for free. A workspace disk, if present, gets a per-fork sparse copy (cp --reflink=auto; falls back to a plain copy on ext4 — a full copy, so fork pre-checks free disk ≥ N × workspace image size and refuses with a clear error if short). v0.3 forks are vsock-only (no NIC) — networked forks require per-fork TAP re-pairing and unique guest network identity, deferred to backlog.
  • P3-3dev flavor from the same pipeline: git, curl, python3, node. Same guarantees, bigger toolbox.
  • P3-4E2B-compatible REST shim (create sandbox / exec / files subset) in shim/; smoke test with the E2B Python SDK pointed at localhost. Document it as best-effort subset.
  • P3-10kelyfos run --workspace ./dir: pack the directory into an ext4 image on the host and attach it as the second virtio-blk drive in the Firecracker drives config at boot (guest /dev/vdb, mounted at /work; rootfs stays /dev/vda). Image size: 2× the directory size, minimum 1 GiB, ceiling configurable in kelyfos.toml. Sync changes back to the host directory on clean shutdown (--no-sync-back to opt out). If the host directory changed during the run, refuse the in-place sync, warn, and write results to ./dir.kelyfos-out instead. Firecracker has no shared-filesystem device — this is the local-files path, and the daily-driver feature.
  • P3-11kelyfos doctor: environment self-check — /dev/kvm present and accessible, nested virtualization, Firecracker version vs versions.mk, vsock availability, free disk for images; detects the host flavor (Lima / WSL2 / bare Linux) and tailors each fix accordingly. Each check prints pass/fail plus the exact fix (mirrors P0-1 and the quickstart). First command the README tells a new user to run.
  • P3-12Policy as code: kelyfos.toml in the project directory declares image, allowlist, secret names, workspace, and resource limits. Bare kelyfos run loads it; explicit flags override. It gets committed to the repo like .devcontainer — the sandbox policy travels with the project. Secret values still come from the host environment or keychain, never from the file.
  • P3-8kelyfos log --export session.html: a self-contained, replayable HTML report of one session — timeline, commands with output, file diffs, egress attempts (blocked in red), secret use by name only. No server; a template rendered over the flight-recorder JSONL. Doubles as the compliance artifact: one file that answers "what did the agent do?"
  • P3-9kelyfos watch: live single-sandbox TUI (Go + bubbletea) — streaming event lane, status line (uptime, egress allowed/blocked counters), quit without affecting the sandbox. Reads the flight recorder only. Source of the launch demo GIF.
  • P3-5Write docs/threat-model.md: what kelyfos defends against (agent-generated code, prompt-injected exfiltration, credential theft from the guest) and explicitly what it does not yet (host-side attacks pre-jailer, side channels, TLS-termination trade-offs from D6). Linked from the README. Launch is blocked until this exists.
  • P3-6CI: GitHub Actions — build BOTH arches; boot-test x86_64 on ubuntu-latest (standard Linux runners expose /dev/kvm; a udev/permissions step is typically required — verify at implementation); boot-test aarch64 on an arm64 runner if it exposes KVM, else build-only there with aarch64 boots covered on the dev machine. Run kelyfos exec "uname -a" as the smoke test, cache Buildroot toolchains per arch. Green pipeline required on main. Includes make bench: reproducible boot-to-ready and snapshot-restore timing (median of 10 runs), published as a CI artifact on every commit — the x86_64 runner numbers are the published reference; Mac-local numbers are informational (nested-virt overhead). Large regressions are flagged in the job summary but don't hard-fail (shared runners jitter). The milliseconds are the marketing.
  • P3-7Public launch: README with 5-minute quickstart, demo GIF, final availability sweep on "KelyfOS" (GitHub, package registries, domains, trademark-level search — name locked in D10), tag v0.3, launch post (HN / blog).

2026-08-22P1-3 Guest boots and talks to the host. image/flavors/base/overlay/init is PID 1: it mounts /proc and /sys (the kernel already mounted devtmpfs on /dev, which is why init has a console at all), then puts a tmpfs-backed overlayfs over the read-only root and pivot_roots into it, carrying /dev, /proc and /sys across first. Two rules shape it: PID 1 never exits — no set -e, every step checked, and an idle loop as the last resort, because a dead init is a kernel panic that turns a small mistake into an unreadable failure — and it degrades loudly, falling back to a read-only root with tmpfs on /tmp and /run and reporting overlay:false to the host rather than failing mysteriously later. D132026-08-22 AF_VSOCK in Go is wrapped by hand in internal/vsock — a small net.Conn and net.Listener over golang.org/x/sys/unix and os.File — rather than taking a vsock library such as mdlayher/vsock. The Go module is single and repo-wide, with the wire format in internal/proto shared by guest and host. Discovered by failing: net.FileListener and net.FileConn reject an AF_VSOCK descriptor outright ("address family not supported by protocol") because Go's net package only parses AF_INET, AF_INET6 and AF_UNIX addresses. Something has to bridge the gap. The whole bridge is about eighty lines, because os.NewFile on a non-blocking descriptor registers it with the runtime poller — so real deadlines and goroutine-friendly blocking come for free and only the two address methods and a poller-aware Accept are left to write. Vsock is the single interface this entire product is built on and it lands in PID 1 at P2-1; owning it outright is worth more than the eighty lines saved, and it keeps the guest's init free of third-party runtime code. One module for both sides means the host and guest cannot disagree about the wire format, because there is only one copy of it.
D142026-08-22 The guest kernel is trimmed well past Firecracker's reference config, and the cuts are a security posture as much as a boot-time one. Removed: all SCSI/iSCSI, XFS, HID and the entire input stack (with CONFIG_VT, since the console is a serial port), the extra I/O schedulers, the virtio devices KelyfOS never attaches (PCI transport, balloon, mem, pmem, console), loop devices, filesystem encryption, module-signature machinery, kernel audit, all network filesystems (NFS/SUNRPC/FUSE), all of netfilter, eBPF, magic-sysrq and profiling. CONFIG_EXPERT=y is enabled because several of these have no Kconfig prompt without it. Kept deliberately: IPv6, cgroups, namespaces, virtio-rng, the PL031 RTC, and DEBUG_KERNEL/SLUB_DEBUG. Every line removes code that this machine cannot reach: there is one virtio-blk disk, one virtio-net NIC, one vsock device and one 16550A UART, and a kernel that cannot load modules will never grow another. Netfilter is the pointed one — KelyfOS enforces egress policy on the host TAP (P2-5) precisely so the guest cannot participate in its own containment, and shipping the guest a firewall it might reconfigure would be arguing with the design. eBPF goes for the same reason a sandbox does not ship a debugger: it is large, privileged and historically exploitable, and seccomp filters (P4-2) are classic BPF and do not need it. DEBUG_KERNEL and SLUB_DEBUG stay because they are menu gates, and turning them off would take CONFIG_DEBUG_LIST — list-corruption detection, a hardening feature — with them. IPv6 stays until P2-5 can actually test egress with it gone; removing it on a guess would be the kind of change that fails three phases later.
D152026-08-22 Boot-time numbers measured under nested virtualisation are informational only. The Lima / vz dev machine does not define pass or fail for any timing claim. The binding measurements — the ≤ 500 ms Phase 1 target and the ≤ 300 ms cold-boot claim in the definition of done — are defined on the P3-6 reference environment: a bare-KVM x86_64 CI runner, measured by make bench the same way P1-7 measures locally (host timestamp to the first frame on the guest-initiated ready channel). P1-7's local median of 899 ms therefore records the dev-machine baseline and does not put the phase target in question. Optimising against that number would be tuning for an artefact of the development environment, and risks trading real guest capability (IPv6, a readable init path) for milliseconds that do not exist on the hardware the claim is actually about. This is the risk table's own position — "Mac-local timings are informational; Linux CI publishes the reference numbers" — promoted from a note to a rule.
D162026-08-22 The guest gets no DNS at all. P2-5 as written says the nftables chain permits "only the host-side proxy port and DNS"; KelyfOS permits only the proxy port. There is no DNS responder on the TAP address, no nameserver in the guest's /etc/resolv.conf, and UDP/53 is dropped like everything else. Name resolution happens in the egress proxy, on the host, as part of deciding whether a connection is allowed. It falls out of the proxy design rather than being an extra restriction: a guest configured with HTTPS_PROXY does not resolve anything itself — it sends CONNECT github.com:443 to the proxy and the proxy resolves. So DNS in the guest is not load-bearing for any traffic KelyfOS intends to allow, and every rule that exists but is never needed is surface without benefit. Removing it also closes the oldest exfiltration channel there is: DNS tunnelling defeats a domain allowlist completely, because the data leaves inside the query names to a resolver that was explicitly permitted, and an allowlist checking hostnames cannot see it. A prompt-injected agent with UDP/53 to anywhere has a working covert channel no matter how careful the HTTP policy is. The cost is honest and worth stating in the threat model: anything that resolves before connecting — ping, raw sockets, a library that ignores proxy environment variables — fails rather than being silently allowed, which is the correct failure for a deny-all sandbox.

D192026-08-22 The P3-1 resync design is endorsed as written and must not be simplified later: mix host-supplied entropy into /dev/urandom first, attempt RNDADDENTROPY credit second and ignore its failure, set the wall clock with clock_settime(CLOCK_REALTIME). Restore is measured through the resync round trip rather than stopping at resume(). Endorsed by John, 2026-08-22. The ordering is load-bearing rather than stylistic. The plain write is what makes N forks of one snapshot diverge: without it every fork resumes with an identical random pool and generates the same session ids, nonces and temporary filenames — a correctness failure that looks like nothing until two forks collide. The RNDADDENTROPY credit is second and optional because it solves a different problem — a restored guest can otherwise block in getrandom(2) waiting for the kernel's entropy estimate to recover, which is how a 100 ms restore becomes a two-second one — and the guaranteed part must not depend on the optional part. Measuring through resync matters for the same reason: stopping at resume() reported 3 ms locally where the honest number, with the guest proven to be answering, is 130 ms. The flattering number was available and is not the one that gets published.
D202026-08-22 The README quickstart installs a prebuilt image from the GitHub release; building from source is the documented alternative, not the default path. The Phase 3 acceptance test requires a person following only the README to reach a working kelyfos exec in ≤ 5 minutes. The from-source path cannot satisfy that under any optimisation: make image compiles a cross toolchain, a kernel and a userland, and takes ~35 minutes on CI hardware. Either the criterion is dropped or the image ships prebuilt, and dropping it would mean the first thing a visitor does with KelyfOS is wait half an hour, which is the opposite of the product's whole claim. So the v0.3 release publishes vmlinux/Image + rootfs.ext4 per arch with a SHA256SUMS file, and make fetch-image (script dev/fetch-image.sh) downloads and verifies them into $(IMAGE_DIR). Artifacts ship gzipped: 141 MB of kernel + rootfs becomes 32 MB, which is most of the quickstart's wall clock. gzip rather than zstd (which would reach 21 MB) because gunzip is on every machine already and the quickstart must not require installing a decompressor. The sums cover the compressed files — that is what gets downloaded — and decompression happens only after they verify, into a temp dir, so a bad download cannot damage an image already in the cache. This is a distribution change, not an architecture change: the artifacts are byte-identical to what make image produces, the build path stays first-class and is what CI exercises on every commit, and the checksums are published so the download is verifiable. It also does not cross a non-goal — the artifacts are static files on a GitHub release, not a hosted service or a registry KelyfOS operates. Signed images and reproducible builds are P4-3; until then the checksum is integrity, not provenance, and dev/fetch-image.sh says so.
D212026-08-22 Every built or fetched image carries an image.json manifest, and the sandbox refuses to boot when the requested flavor does not match it. Found while preparing the v0.3 release: ImageDir() resolves to out/<arch> with no flavor component, so --image was a label that selected nothing. Build base, run --image dev, and the sandbox boots base while the flight recorder writes image: dev into session.start. That is not a cosmetic bug: the entire value proposition of the recorder is that it is the one account of the session the guest cannot influence, and here the host was writing a field it had never checked. An audit record that is confidently wrong is worse than one that is absent. Rejected the alternative of making the path flavor-scoped (out/<arch>/<flavor>/): it is the tidier model, but it invalidates every existing cache and snapshot workspace_path, and it still would not stop a hand-placed rootfs from being mislabelled. The manifest fixes the actual defect — the host asserting an unverified fact — and it earns its keep twice more: it is the provenance record the release artifacts needed anyway (arch, flavor, kernel and rootfs digests, pinned Buildroot/Linux versions, build date), and it lets fetch-image tell you what you just downloaded. make image and dev/fetch-image.sh both write it; a missing manifest is a hard error naming the fix rather than a silent fallback, because a silent fallback is how the original bug survived this long.
D222026-08-22 kelyfos snapshot restore re-creates the egress path and re-pairs the guest's NIC to a fresh TAP via Firecracker's network_overrides. Forks stay vsock-only exactly as P3-2 specifies. The Phase 3 acceptance test surfaced this: step 1 prepares a sandbox by cloning a repo inside it, which requires a NIC, and step 2 restores that snapshot. Restore had only ever been exercised on vsock-only machines, so it failed — and failed badly. With the parent still running, Firecracker reported Resource busy on the original TAP; with the parent gone, Operation not permitted, because the TAP no longer existed and nothing re-created it. Either way the user had already paid for a 512 MB snapshot that could never be loaded, and the error they saw was a raw Firecracker fault string about ifreq structures. P3-2 deliberately scopes forks to vsock-only, and that stands: N forks would need N distinct guest network identities, and the guest's address and default route are baked into the memory image, so genuinely separating them needs a network namespace per fork — which is P4-1 jailer territory. But P3-1 never scoped restore that way, and restore is the tractable case precisely because there is only one machine: it can re-use the original addressing. The mechanism was already available and simply unused — Firecracker's PUT /snapshot/load takes network_overrides (host device re-pairing per interface) alongside the vsock_override KelyfOS already passes. Restore now builds the egress path in the same order run does (TAP, proxy, firewall, then the machine), loads with the override, and re-installs the trust anchor over the control channel — necessary because D6 mints a fresh CA per run, so a restored guest is otherwise carrying an anchor for a CA that no longer exists. fork now refuses a networked snapshot with a message that says so, instead of emitting the same Firecracker fault four times.
D232026-08-22 kelyfos run [flags] -- <command> runs that command on the host for the lifetime of the sandbox, exports KELYFOS_SANDBOX to it, and exits with its status. Section 1's definition of done names this exact invocation — kelyfos run --image dev --workspace . --allow github.com --secret GITHUB_TOKEN@github.com -- <agent cmd> — and it did not exist: run took no positional arguments at all, so the only way to use a sandbox was run & followed by exec. Found while checking §1 line by line rather than assuming it was covered, since the PLAN-FEATURES activation gate depends on §1 being met. The bullet also settles what the command is: it says the agent “operates only through MCP tools on your project files”. An agent running inside the guest would not use MCP tools, it would just use the filesystem. So the trailing command runs on the host, reaching the sandbox over the MCP bridge — which is also the shape that makes the secret guarantee meaningful, since the value stays on the host side of the proxy and never enters the guest either way. sandbox.Load now falls back to $KELYFOS_SANDBOX when no --sandbox is given, so the child's kelyfos mcp and kelyfos exec attach to the right machine even when other sandboxes are running — previously an empty id meant “the only running one” and simply failed when there were several. Teardown, workspace sync-back and the flight recorder's session.end all run on the child's exit, so the sandbox's lifetime is exactly the command's.
