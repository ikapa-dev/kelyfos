section 1

End goal & definition of done

Mission. Build the guest OS layer that every agent-sandbox platform treats as an afterthought: a tiny, immutable Linux image whose init system speaks MCP, with security policy and auditability baked into the image itself — self-hostable on any Linux/KVM box, portable across microVM runtimes.

The project is done (v1.0-worthy) when all of the following are true:

  • A fresh user goes from git clone to a working sandboxed agent command in under 5 minutes on a stock Linux/KVM machine.
  • kelyfos run --image dev --workspace . --allow github.com --secret GITHUB_TOKEN@github.com -- <agent cmd> works as advertised: the agent operates only through MCP tools on your project files, egress outside the allowlist fails, and the secret value never exists inside the guest.
  • Boot-to-ready ≤ 300 ms cold, ≤ 100 ms from snapshot; kelyfos fork -n 4 yields four divergent copies of a prepared environment.
  • Every session produces a complete, tamper-evident (hash-chained) audit log — live (kelyfos log --follow, kelyfos watch) and exportable as a standalone, verifiable HTML session report.
  • An E2B-compatible API shim passes an SDK smoke test, so existing code can point at a self-hosted kelyfos box.
  • Published as open source with a README, quickstart, and demo; John uses it for his own Claude Code runs (dogfooding).

Strategic intent: reputation, learning, and consulting leads first. The one commercial thread worth keeping alive is the EU-compliance / self-hosted angle (hardened, auditable images + support for European teams). Revenue is a bonus, not the goal.

section 2

What we are building

ComponentDescription
image/ A Buildroot pipeline producing two artifacts: a stripped vmlinux (virtio-only, no modules) and a read-only ext4 rootfs (target < 200 MB) with a tmpfs overlay for writes. Flavors: base, dev, later browser.
supervisor/ The novel software. One static Go binary running as PID 1 inside the guest: mounts, zombie reaping, and an MCP server over vsock exposing the machine as tools — exec, read_file, write_file, list_dir, upload/download. No SSH, no shell login, no cloud-init. The sandbox is a toolbox, not a computer.
host/ The kelyfos CLI (Go): assembles Firecracker config, boots/stops VMs, bridges MCP to stdio, runs the egress proxy (deny-all + domain allowlist), injects secrets at the proxy so credentials never enter the guest, packs and syncs --workspace directories, self-checks the environment (kelyfos doctor), and writes the flight recorder (append-only, hash-chained JSONL of every tool call and network attempt).
shim/ E2B-compatible REST subset (create sandbox / exec / files) so existing SDK users can point at a self-hosted kelyfos host. Adoption hack, phase 3.
snapshots First-class snapshot/restore/fork via Firecracker snapshots: clock resync, entropy, network re-init handled correctly so one prepared environment forks into N parallel branches.

Non-goals — hard boundaries

  • No new kernel. Stock Linux, custom config only.
  • No VMM. Firecracker (cloud-hypervisor later, maybe). We ship what boots inside it.
  • No orchestrator, no control plane, no hosted service, no web dashboard. Single-host CLI; monitoring is read-only viewers over the flight recorder (decision D7). Fleet management is someone else's product.
  • No GUI desktop / computer-use layer in v0.x. Headless browser flavor is the closest we get, and only in phase 4.
  • No Kubernetes integration in v0.x.
Scope discipline is the project's survival strategy. Every one of these non-goals has a funded startup already doing it. The guest image is the empty niche — stay in it.

section 3

Why this exists

The runtime layer is crowded (E2B, Daytona, Beam, Temps, PandaStack, Microsandbox, OpenComputer, Northflank, Modal…). All of them build control planes and boot a generic Ubuntu/Alpine rootfs inside. Nobody ships the guest itself as an opinionated, portable product: MCP-native init, deny-all egress, secrets kept outside the VM, audit-first design. The analogy is Talos Linux — Talos didn't compete with Kubernetes, it became the OS purpose-built to be run by it.

Differentiators, in priority order: (1) agent-native interface — the guest is a set of MCP tools, not a computer with a shell; (2) auditability — a replayable flight recorder nobody else offers out of the box; (3) self-hosted and EU-friendly — data residency is the one buying reason the US-hosted platforms cannot serve.

Phase 1 — Minimal bootable guest (v0.1 · "it boots")

TODO

Goal: a self-built kernel + rootfs that boots under Firecracker and answers one command over vsock. Est. 3–4 weekends.

  • P1-0Spec before code — write docs/protocol.md covering: (a) Firecracker's hybrid vsock model — the guest speaks AF_VSOCK, but the host side is a dedicated Unix domain socket (this is not the Firecracker API socket, and no host vsock kernel module is involved): host-initiated connections open the vsock UDS and send CONNECT <port>\n, guest-initiated connections to host CID 2 port N land on <uds_path>_<port>; (b) project constants: vsock.guest_cid = 3 and the port assignments (exec, log, MCP channels); (c) the newline-delimited JSON frame schema for exec (request id, cmd, stdin, timeout; response chunks: stream, data, exit code); (d) MCP framing for phase 2: newline-delimited JSON-RPC per the MCP stdio transport spec — "Messages are delimited by newlines, and MUST NOT contain embedded newlines" (spec §Transports, all revisions incl. 2025-11-25); explicitly not LSP Content-Length framing — so the kelyfos mcp bridge is a pass-through. All later tasks implement this document.
  • P1-1Buildroot external tree parameterized by ARCH (aarch64 primary — the dev machine; x86_64 second): musl, BusyBox; make toolchain downloads and prepares Buildroot pinned to a release, defaulting ARCH to the build host.

Artifact formats are strict: aarch64 must produce the uncompressed Image build target (not Image.gz); x86_64 must produce the uncompressed ELF vmlinux (Firecracker does not boot bzImage). The fragments must also state # CONFIG_MODULES is not set explicitly — "no loadable modules" is a config assertion, not a hope.

  • P1-4make image outputs the kernel artifact (Image on aarch64, vmlinux on x86_64) + rootfs.ext4; rootfs < 200 MB.
  • P1-5kelyfos run (Go, in host/): write Firecracker config JSON, boot the VM, clean teardown on Ctrl-C.
  • P1-6kelyfos exec "<cmd>": newline-delimited JSON over Firecracker's vsock UDS → run in guest → return stdout, stderr, exit code.
  • P1-7Measure boot-to-ready (host timestamp → first vsock heartbeat). Record the number in the progress log. Target this phase: ≤ 500 ms.
  • P1-8Cross-arch gate: make image ARCH=x86_64 cross-builds cleanly on the aarch64 dev machine (build only — no local boot required). From this point it must keep passing on every commit; boot verification for x86_64 lands with CI in P3-6. Pulled forward so x86-specific breakage is caught in days, not weeks.

Phase 2 — Agent-native supervisor (v0.2 · "a toolbox, not a computer")

TODO

Goal: the differentiating layer — MCP as the only interface, policy and audit built in. Est. 3–4 weekends.

  • P2-0Design gate before P2-5/P2-6 — HTTPS makes plain CONNECT tunneling incompatible with header injection, so choose the TLS strategy: (a) TLS-terminating proxy with a per-install kelyfos CA baked into the guest trust store (transparent injection, MITM within your own box), or (b) CONNECT-only tunnel plus a guest-side credential helper that fetches short-lived tokens from the supervisor (no MITM, needs tool cooperation). Prototype the riskiest part, record the choice as decision D6, then implement P2-5/P2-6 accordingly.
  • P2-1Supervisor as PID 1 (static Go binary): mounts, zombie reaping, clean shutdown on vsock command. Replaces the P1 init script.
  • P2-2MCP server over vsock with tools: exec (streaming stdout/stderr), read_file, write_file, list_dir, upload, download.
  • P2-3kelyfos mcp: stdio ⇄ vsock bridge so any MCP client (Claude Code first) can attach to a running sandbox.
  • P2-4Flight recorder: every tool call and result appended as JSONL on the host; kelyfos log [--follow] replays a session. Stable, versioned event schema documented in docs/events.md (command start / output / exit, file writes, egress allowed / blocked, secret use by name — never values). Each event embeds the hash of the previous event, making every session log a tamper-evident chain verifiable with kelyfos log --verify. The P3 viewers build on this contract; the schema is the product, viewers are replaceable.
  • P2-5Egress off by default (no NIC). --allow d1,d2 boots with a NIC: the CLI creates a per-VM TAP (ip tuntap add kelyfos<id> mode tap, /30 point-to-point addressing, no NAT and no IP forwarding — none is needed, because the proxy and DNS responder bind directly on the host's TAP address, so guest traffic terminates on the host and only the proxy process itself can reach the internet) and installs an nftables chain on it permitting only the host-side proxy port and DNS, dropping everything else; the guest gets HTTP_PROXY/HTTPS_PROXY pointing at the proxy (HTTP(S) CONNECT + DNS restricted to the allowlist). The exact nftables rule template is written into docs/networking.md as part of this task. Every attempt (allowed or blocked) is logged.
  • P2-6Secret injection: --secret NAME@domain — the proxy attaches the credential to matching requests; the value never appears in guest env, disk, or logs.
  • P2-7End-to-end dogfood: Claude Code attached via kelyfos mcp completes a small real task (clone a repo, edit, run tests) entirely inside the sandbox.

Acceptance test — recreate & verify

  1. kelyfos run --image base --allow github.com → sandbox up.
  2. Attach an MCP client via kelyfos mcp → tool list shows the six tools.
  3. Inside: exec "git clone https://github.com/octocat/Hello-World" → succeeds (allowlisted).
  4. Inside: exec "curl -m 5 https://example.com" → fails; the attempt appears as blocked in kelyfos log.
  5. With --secret GITHUB_TOKEN@github.com: an authenticated API call succeeds, and exec "env" shows no token.
  6. kelyfos log replays the full session in order.
  7. kelyfos log --verify passes on the session; flipping one byte in the JSONL makes it fail.

Phase 3 — Snapshots, flavors, compatibility (v0.3 · "fork it")

TODO

Goal: the performance story, the daily-driver UX, and the adoption hack — then go public. Est. 5–7 weekends.

  • P3-1kelyfos snapshot save|restore via Firecracker snapshots. On resume the host sends a resync RPC over vsock — wall-clock timestamp plus fresh random bytes — and the supervisor applies them with clock_settime(CLOCK_REALTIME) and a write to /dev/urandom (ptp_kvm + chrony considered and rejected: too heavy for a BusyBox image). Target restore ≤ 100 ms.
  • P3-2kelyfos fork -n N: N restores from one snapshot, with the mechanism made explicit. The rootfs block device is opened read-only and shared by all forks — divergent writes already live in the in-guest tmpfs overlay, which is part of guest memory; each fork maps the memory snapshot file privately (MAP_PRIVATE), so the OS provides page-level copy-on-write for free. A workspace disk, if present, gets a per-fork sparse copy (cp --reflink=auto; falls back to a plain copy on ext4 — a full copy, so fork pre-checks free disk ≥ N × workspace image size and refuses with a clear error if short). v0.3 forks are vsock-only (no NIC) — networked forks require per-fork TAP re-pairing and unique guest network identity, deferred to backlog.
  • P3-3dev flavor from the same pipeline: git, curl, python3, node. Same guarantees, bigger toolbox.
  • P3-4E2B-compatible REST shim (create sandbox / exec / files subset) in shim/; smoke test with the E2B Python SDK pointed at localhost. Document it as best-effort subset.
  • P3-10kelyfos run --workspace ./dir: pack the directory into an ext4 image on the host and attach it as the second virtio-blk drive in the Firecracker drives config at boot (guest /dev/vdb, mounted at /work; rootfs stays /dev/vda). Image size: 2× the directory size, minimum 1 GiB, ceiling configurable in kelyfos.toml. Sync changes back to the host directory on clean shutdown (--no-sync-back to opt out). If the host directory changed during the run, refuse the in-place sync, warn, and write results to ./dir.kelyfos-out instead. Firecracker has no shared-filesystem device — this is the local-files path, and the daily-driver feature.
  • P3-11kelyfos doctor: environment self-check — /dev/kvm present and accessible, nested virtualization, Firecracker version vs versions.mk, vsock availability, free disk for images; detects the host flavor (Lima / WSL2 / bare Linux) and tailors each fix accordingly. Each check prints pass/fail plus the exact fix (mirrors P0-1 and the quickstart). First command the README tells a new user to run.
  • P3-12Policy as code: kelyfos.toml in the project directory declares image, allowlist, secret names, workspace, and resource limits. Bare kelyfos run loads it; explicit flags override. It gets committed to the repo like .devcontainer — the sandbox policy travels with the project. Secret values still come from the host environment or keychain, never from the file.
  • P3-8kelyfos log --export session.html: a self-contained, replayable HTML report of one session — timeline, commands with output, file diffs, egress attempts (blocked in red), secret use by name only. No server; a template rendered over the flight-recorder JSONL. Doubles as the compliance artifact: one file that answers "what did the agent do?"
  • P3-9kelyfos watch: live single-sandbox TUI (Go + bubbletea) — streaming event lane, status line (uptime, egress allowed/blocked counters), quit without affecting the sandbox. Reads the flight recorder only. Source of the launch demo GIF.
  • P3-5Write docs/threat-model.md: what kelyfos defends against (agent-generated code, prompt-injected exfiltration, credential theft from the guest) and explicitly what it does not yet (host-side attacks pre-jailer, side channels, TLS-termination trade-offs from D6). Linked from the README. Launch is blocked until this exists.
  • P3-6CI: GitHub Actions — build BOTH arches; boot-test x86_64 on ubuntu-latest (standard Linux runners expose /dev/kvm; a udev/permissions step is typically required — verify at implementation); boot-test aarch64 on an arm64 runner if it exposes KVM, else build-only there with aarch64 boots covered on the dev machine. Run kelyfos exec "uname -a" as the smoke test, cache Buildroot toolchains per arch. Green pipeline required on main. Includes make bench: reproducible boot-to-ready and snapshot-restore timing (median of 10 runs), published as a CI artifact on every commit — the x86_64 runner numbers are the published reference; Mac-local numbers are informational (nested-virt overhead). Large regressions are flagged in the job summary but don't hard-fail (shared runners jitter). The milliseconds are the marketing.
  • P3-7Public launch: README with 5-minute quickstart, demo GIF, final availability sweep on "KelyfOS" (GitHub, package registries, domains, trademark-level search — name locked in D10), tag v0.3, launch post (HN / blog).

section 8

Developer protocol — how Claude Code works on this project

This file (PLAN.html) is the single source of truth. Read it fully before any session. Then follow these rules, in order:

  • 1. Pick work top-down. Take the first unchecked task in the lowest-numbered phase that is not done. List position defines order; task IDs are stable labels and may be non-sequential. Do not skip ahead across phases without a decision-log entry.
  • 2. Small commits. Reference task IDs in commit messages: P1-6: exec over vsock.
  • 3. Record completion in this file. When a task is verified working: add the checked attribute to its checkbox in the markup, and append a row to the Progress Log (date, task ID, what changed, evidence: the exact command run and a trimmed output snippet). The dashboard bars compute from the markup, not from browser clicks.
  • 4. Close phases with the acceptance test. Run the phase's acceptance steps verbatim, paste evidence into the Progress Log, set the phase's data-status="done" and its badge text to DONE, set the next phase to active / ACTIVE, and update the "Current focus" line (#focus) and header status (#meta-status).
  • 5. Log deviations. Any change of approach, library, or scope gets a Decision Log row with rationale before implementation. Non-goals in section 2 are hard boundaries — do not cross them; propose a decision-log entry and stop if a task seems to require it.
  • 6. Append, never rewrite history. Log rows are immutable. Update #meta-updated with today's date on every edit of this file.
  • 7. Blocked? Mark the task with [BLOCKED: reason] appended to its text, log it, and move to the next task. Surface all blockers at the end of the session summary.

Decision log

IDDateDecisionRationale
D12026-08-21 Build the guest image + single-host CLI; explicitly not a kernel, VMM, control plane, or hosted service. The only under-served niche in a crowded market; solo-sized; portable across runtimes.
D22026-08-21 Buildroot for v0.x; revisit a Nix flake in phase 4. Fastest path to first boot; reproducible-build story can come later with signing/SBOM.
D32026-08-21 Go for supervisor and CLI. Single static binaries, trivial cross-compilation, fast iteration. Revisit Rust only if binary size or startup cost becomes a measured problem.
D42026-08-21 "agos" is a working title. Collision check is a launch-gate task (P3-7), not a today problem.
D52026-08-22 License: Apache-2.0, with DCO sign-off required on all contributions from day one. Decided by John, 2026-08-22. KelyfOS is positioned as the portable guest image other runtimes adopt — AGPL would block commercial runtimes from embedding it and fight the distribution strategy. The EU-compliance thread sells services and signed artifacts, not code exclusivity, so it survives under Apache (the Talos / Red Hat model). Matches the ecosystem: Firecracker itself is Apache-2.0. DCO keeps a future relicensing move possible. Executed in P0-7.
D6pending TLS strategy for egress + secret injection (terminating proxy with local CA vs CONNECT + credential helper). To be recorded at the P2-0 design gate. Referenced by: P2-0, P3-5.
D72026-08-21 Monitoring = readers of the flight-recorder JSONL only: HTML session export (P3-8) and terminal TUI (P3-9, P4-6). No web dashboard — no server with auth, persistence, or a fleet view. A localhost read-only viewer is the absolute ceiling, and only on demonstrated community demand. A dashboard is a control plane — non-goal territory where funded competitors live. Litmus test for any monitoring feature: does it read the JSONL, or does it manage sandboxes? Readers are fine; managers are scope creep.
D82026-08-21 Daily-driver and trust features adopted: workspace block-device sync (P3-10), kelyfos doctor (P3-11), kelyfos.toml policy-as-code (P3-12), hash-chained audit (P2-4) with signed exports (P4-3), CI benchmark (P3-6). Phase 3 re-estimated to 5–7 weekends. Approved by John, 2026-08-21. Differentiators no competitor ships as a set; all stay inside the non-goals (single-host, readers not managers, policy in files not servers).
D92026-08-22 Dev machine = MacBook Pro M5 Max / 64 GB: macOS 15+ → Lima (vz, nested virtualization) → Linux → Firecracker. aarch64 is the primary architecture; x86_64 is cross-built and gated from Phase 1 (P1-8) and is the CI reference. Host support model = the Docker Desktop pattern (P4-7): one CLI everywhere, transparently managed Linux layer on macOS/Windows; Firecracker itself always runs on Linux/KVM. Approved by John, 2026-08-22. Fastest compile loop for the Buildroot/kernel-heavy phases; 64 GB enables the many-fork demo; aarch64-first covers Graviton and cheap EU ARM hosting; the early x86 gate prevents drift. Native macOS backend (libkrun) stays a backlog experiment, not v0.x scope.
D102026-08-22 Project named KelyfOS — κέλυφος (kélyfos), "shell". CLI binary kelyfos, config kelyfos.toml, TAP prefix kelyfos<id>. Supersedes the "agos" working title (D4). Chosen over KratOS: "kratos" is heavily occupied in adjacent open source (a major Go microservices framework whose CLI binary is literally kratos, the Ory Kratos identity server) plus a listed defense contractor — bad findability and a PATH collision for a Go CLI. KelyfOS has clean airspace and the metaphor is literal: a shell wrapped around the agent. Final availability sweep stays gated at launch (P3-7).

section 11

Risks & constraints

RiskMitigation
KVM requires Linux; the dev machine is macOS (M5 Max). Lima VM with vz + nested virtualization (M3+, macOS 15+) is the primary path — verified by P0-1 and kelyfos doctor. WSL2 and bare Linux boxes are equal-citizen alternates. Nested-virt overhead means Mac-local timings are informational; Linux CI publishes the reference numbers.
Fast-moving, consolidating market; a platform ships the same idea as a feature. Ship small and publicly early (v0.1–v0.3 in months, not a year). The portable-guest positioning survives even if runtimes bundle their own images.
Solo time budget; motivation decay. Phases sized at 2–4 weekends each, every one ends in a demo-able checkpoint. Momentum over completeness.
Scope creep toward orchestration. Non-goals in section 2 are enforced by developer protocol rule 5.
Security claims invite scrutiny. Document the threat model honestly in the README (what kelyfos defends against, what it doesn't). Jailer + hardening land in phase 4 before any strong claims.
Do not market security guarantees before P4-1 and P4-2 are done. Until then the story is "isolation-first architecture," not "hardened."
