Epic E1 — Resource governance (v0.4)

ACTIVE

Goal: the user decides exactly how much machine the agent gets — and can prove the limits held. The build plan targets the caps that are free at boot time (vCPU count, RAM, disk size — the VM’s hardware, enforced by KVM), added to it by a same-day amendment (D11). Because the build run started in parallel with that amendment, E1-0 first establishes which revision actually shipped. This epic then adds the enforcement-grade layer: host CPU-time quotas, I/O throttling, scratch caps, time budgets, and a usage receipt for every session. Everything enforces host-side (F-D2): the guest runs untrusted code and polices nothing. Estimate: 2–3 weekends.

  • E1-0Baseline reconcile — establish what v0.1 actually shipped before building on it. Check the repo’s PLAN.html for the resource-caps amendment — match by content, not decision number (the run logs its own decisions, so “D11” may be taken by something else). The knobs to look for: --cpus/--mem in P1-5, --disk in P3-10, [resources] defaults in P3-12. Present and implemented → verify with a quick boot test and move on. Absent (the run started from a pre-amendment copy) → implement those knobs now as the first work of this epic and add a decision row here noting they shipped in v0.4 rather than v0.1. Either way, log the finding — every task below assumes the knobs exist.
  • E1-1docs/resources.md — semantics & precedence spec, written before code. The [resources] keys in kelyfos.toml become hard ceilings; CLI flags request within them; a flag exceeding its ceiling refuses at boot with an error naming the ceiling and the toml line it came from (this upgrades the v0.1 “flags override toml” behavior — note it in the doc). Units: cpus integer; mem/disk/scratch human sizes (512M, 2G); cpu_quota a percentage of a single core’s worth of CPU time (100% = one core’s worth; 150% = 1.5 cores’ worth — an absolute quota, exactly the E1-2 mapping). One table lists every cap and the host mechanism that enforces it: KVM machine config, cgroup v2, Firecracker rate limiter, tmpfs mount option, host timer, device size.
  • E1-2Host CPU-time quota: launch each Firecracker process inside its own cgroup v2 slice; cpu_quota (e.g. "150%" = 1.5 cores) is translated by the CLI into cgroup v2 cpu.max integer microseconds with a 100 ms period — "150%" → 150000 100000, "50%" → 50000 100000; the percentage string never touches the kernel. Document the distinction this creates: cpus caps parallelism (cores the guest sees), cpu_quota caps actual host CPU time. Standalone implementation now; folds into the jailer if PLAN.html P4-1 ever lands.
  • E1-3I/O throttling via Firecracker’s native token-bucket rate limiters on the network device and both block devices — configuration of an existing Firecracker feature, no new machinery. Toml keys: net_mbps_rx, net_mbps_tx, disk_iops, disk_mbps → rate_limiter objects in the drive / network-interface API config.
  • E1-4OOM visibility: the RAM cap is already absolute (VM hardware) — make hitting it legible. The supervisor (PID 1) watches /dev/kmsg for guest OOM-killer events and emits a resource.oom flight-recorder event naming the killed process; kelyfos run’s exit distinguishes “agent was OOM-killed” from a crash.
  • E1-5Scratch cap, named precisely: the P1-3 init mounts one tmpfs that backs the overlayfs upperdir/workdir over the read-only root — that tmpfs mount receives an explicit size= from resources.scratch (default 50% of the guest’s RAM — the guest kernel’s own default, i.e. relative to the --mem cap, not host memory — now stated instead of implied). All writes outside /work land on it and hit ENOSPC at the cap instead of silently consuming the RAM budget; the workspace disk at /work is a separate block device and unaffected.
  • E1-6Time budgets: --max-runtime and --idle-timeout flags + toml keys. Idle = no vsock RPC and no egress-proxy traffic for the window. On expiry: SIGTERM to the agent → grace period → workspace sync-back → teardown, plus a resource.timeout audit event recording which budget fired.
  • E1-7Usage vs caps, live and after: kelyfos watch gains a resources lane (CPU% vs quota, mem vs cap, disk vs device size, net vs limiter), sampled from the VM slice’s cgroup v2 cpu.stat / memory.current deltas at a ~1 s tick. At teardown the flight recorder gets a resource.summary event — peak RSS, CPU-seconds, bytes tx/rx, disk bytes written — so every session ends with a usage receipt that kelyfos log --export renders.
  • E1-8Enforcement proof: add stress-ng to the dev flavor; drive CPU, memory, disk, and network against deliberately tight caps and verify from the host that each one held. Numbers go in the progress log the same way P1-7’s boot times did.

Acceptance test — recreate & verify

  1. kelyfos run --image dev --cpus 1 --mem 512M --disk 1G with toml: cpu_quota="50%", net_mbps_rx=10, max_runtime="60s".
  2. In-guest stress-ng --cpu 4 → host cgroup stats show ≤ 50% of one core consumed.
  3. In-guest dd into /work → ENOSPC at the 1 GiB device size; same into scratch → ENOSPC at the scratch cap (unset in step 1, so the default applies: 50% of the 512M guest RAM = 256M).
  4. Download from an allowlisted local test server → observed throughput ≤ 10 Mbps.
  5. Let the 60 s budget fire → graceful teardown, workspace sync-back completed, exit status says timeout.
  6. kelyfos log --verify passes; the log contains resource.timeout and resource.summary; kelyfos log --export renders the usage receipt.
  7. A flag exceeding a toml ceiling (--cpus 8 vs cpus=2) refuses at boot, naming the ceiling.

Exit checkpoint: tag v0.4 — “the user decides how much machine the agent gets.”

Epic E2 — Agent teams (v0.5)

QUEUED

Goal: user-declared multi-agent topologies on one host — isolated agents, enforced edges, shared state, full team audit. A [team] section in kelyfos.toml declares agents and the edges between them; kelyfos team up boots the graph. Think docker-compose for agent teams: master–workers, full mesh, pipelines, or islands — the edge list is the topology. The agents’ reasoning (who delegates what) stays in the agent framework; KelyfOS provides the enforced substrate: no guest ever has a network path to another guest — every inter-agent message transits the host broker over the existing vsock channels, is checked against the edge list, and lands in the hash-chained flight recorder. In scope per F-D3 (single-host only); fleet orchestration remains a non-goal. Builds on E1 (team budgets are cgroup hierarchies), P2-4/P2-5 (audit + egress), and P3-2 (fork makes team spawn milliseconds-class — the build plan’s restore target, to be confirmed by its P3 measurements). Estimate: 5–7 weekends — the largest epic in the project.

  • E2-0docs/teams.md — spec first. Toml schema: [team] name; [[team.agent]] name / image / [resources] per agent / per-agent egress allowlist & secrets; [[team.edge]] from / to / bidirectional (default true). Broker semantics: send, recv, ask/reply (correlated question→answer with a timeout — the primitive agents actually need), team-store access; delivery is at-most-once with explicit errors, no queues-as-a-service. Threat model in the same doc: no guest-to-guest network path exists at all; no edge → message refused and audited; declared topology is fixed for the run — no live rewiring, with exactly one sanctioned exception: an E2-5 runtime spawn joins with a single edge to its spawner (plus store access per the spawn budget); nothing else changes without a restart. Two clarifications the spec must state: the flight recorder logs message outcomes and is not a delivery buffer — at-most-once delivery and the durable audit log are orthogonal; delivered messages are FIFO per edge. And edge direction: a unidirectional edge is visible in team_peers to the initiating side only; replies to an ask travel the return path of that ask and need no edge of their own.
  • E2-1Broker in the host CLI: routes messages between VM supervisors over the existing per-VM vsock channels, enforcing the edge list. Every message becomes a flight-recorder event — metadata always (from, to, size, hash); payload capture is a per-team toml switch so sensitive teams can log hashes only. Refused sends (no edge) are their own event type.
  • E2-2Guest side: the supervisor exposes team capability as MCP tools — team_send, team_recv, team_ask (ask a peer a question and wait for the answer; the broker correlates the reply and enforces the timeout), team_reply, team_peers, team_store_get / team_store_put. Incoming questions surface to the receiving agent as ordinary MCP tool events, so answering is natural for an LLM. team_peers returns only the agents this node can initiate to (edge-direction rule in E2-0) — an agent cannot enumerate the rest of the team.
  • E2-3Team store: host-side key/blob store per team, the “shared knowledge” mechanism. Per-key access rules (owner / listed agents / whole team). Stated plainly in the docs, as two separate facts with separate reasons: cross-VM shared RAM is impossible here because Firecracker ships no shared-memory device (its minimal model — F-D1’s sibling fact); concurrent read-write mounting of one ext4 disk is impossible because ext4 is not a cluster filesystem — true on any VMM, nothing to do with Firecracker; read-only multi-mounting is fine, and is exactly what the build plan’s fork design does with the shared rootfs. The store is the safe equivalent, and unlike shared memory every access is permissioned and audited.
  • E2-4kelyfos team up | ps | down: boot the declared graph (fork from a shared snapshot when agents use the same image — five warm workers in milliseconds-class time per the build plan’s restore target; a target until P3 measures it), per-agent workspaces, ps shows agents + edge counts + resource use, down tears down all VMs and syncs all workspaces.
  • E2-5Master spawn capability: an agent whose toml grants team.spawn may request workers at runtime within a declared budget — max count, per-worker resource ceilings, image whitelist, lifetime. The host enforces the budget; every spawn/despawn is an audit event. A spawned worker attaches with exactly one edge — to its spawner — plus whatever store access the budget template grants (the E2-0 exception). The decision to spawn stays agent-side; KelyfOS only enforces what was pre-authorized by the user.
  • E2-6Team resource budget: each team gets a parent cgroup v2 slice — the collective cap — with per-agent E1-2 slices as children; cpu.weight divides contention fairly inside the team. This absorbs the old “fair-share” parking-lot item, scoped to a team; host-wide or cross-team scheduling remains out of scope (fleet territory).
  • E2-7Team transcript: kelyfos log --verify covers the whole team chain; kelyfos log --export team.html renders per-agent lanes with message flow between them — a replayable record of who told what to whom, with the store accesses inline.
  • E2-8kelyfos watch multi-lane team view: one lane per agent (exec activity, egress, resource use vs caps) plus a message-flow ticker. Supersedes the build plan’s P4-6 idea for the team case.
  • E2-9Proof demo, scripted and committed: 1 master + 4 fork-spawned workers; master splits a task via team_send, one worker team_asks the master a clarifying question mid-task, workers coordinate results through the team store, master assembles the answer. A deliberate edge violation (worker→worker with no edge) must be refused and logged. Teardown leaves synced workspaces and a verifiable transcript.

Acceptance test — recreate & verify

  1. kelyfos team up on the committed demo toml (1 master, 4 workers, star topology + store) → 5 VMs boot; workers spawn via fork, total spawn time recorded — the < 1 s bar binds on the P3-6 reference environment, local nested-virt numbers are informational (per the build plan’s P1-7 decision).
  2. kelyfos team ps shows all five, their edges, and live resource use against E1 caps.
  3. The demo task completes end-to-end through team_send/team_recv, at least one team_ask round-trip, and the team store.
  4. A worker attempts to message a worker it has no edge to → refused, and the refusal appears in the log.
  5. An agent without team.spawn attempts a spawn → refused + audited; the master’s spawn beyond its budget cap → refused + audited; one budgeted spawn by the master succeeds, the new worker attaching with a single edge to the master.
  6. Host cgroup stats show the team’s collective cap held while all five run stress-ng.
  7. kelyfos team down → all VMs gone, all workspaces synced.
  8. kelyfos log --verify passes for the whole session; kelyfos log --export team.html renders the five-lane transcript including the refused events.

Exit checkpoint: tag v0.5 — “agent teams as code.”

Epic E4 — MCP surface (v0.7)

QUEUED

Goal: MCP in both directions. Outward: kelyfos serve-mcp makes KelyfOS a tool for any MCP client — Claude Code, Cursor, anything — one config line and the client’s agent gains sandbox_run, sandbox_exec, snapshots, and team control, so risky commands execute inside a VM instead of the developer’s machine. Inward: [[plugin]] entries in kelyfos.toml declare extra MCP servers the agent gets inside the guest (e.g. a browser-control server), namespaced, policy-bound, and audited per call. Two standing principles (F-D5): serve-mcp can never widen policy — the project’s toml is the ceiling, and no tool exists to change it; and in-guest plugins are safe because they run inside the same isolation — a malicious plugin has exactly the powers of a malicious agent, which the sandbox already assumes. Distinct from the per-VM kelyfos mcp bridge (P2-3), which fronts one guest’s supervisor. Builds on E2 (team tools) and E3 (generated reference auto-covers the new surface). Estimate: 3–5 weekends.

  • E4-0docs/mcp-surface.md — spec first, both directions. Host tool list with schemas; the policy-ceiling rule stated as an invariant; plugin tool namespacing (<plugin>.<tool>); the plugins-drive layout and per-plugin manifest; session/concurrency model with max_sandboxes (toml [mcp] section, small default). Framing note carried over: MCP stdio is newline-delimited JSON-RPC — settled (verified against the official MCP spec, all revisions through 2025-11-25, during the build-plan review rounds); do not relitigate.
  • E4-1kelyfos serve-mcp core: stdio MCP server wrapping the existing host machinery — sandbox_run (boot with the project’s toml policy), sandbox_exec, sandbox_stop, sandbox_list; multiple concurrent sandboxes with ids; max_sandboxes enforced; requests exceeding the toml ceilings refused with the E1-1 error style.
  • E4-2File and state tools over existing machinery: sandbox_read_file / sandbox_write_file (supervisor RPCs), sandbox_snapshot / sandbox_fork / sandbox_restore (P3 snapshot layer).
  • E4-3Team tools: team_up / team_ps / team_down as thin wrappers over E2 — an external agent can raise and retire a whole declared team, still bounded by the team toml.
  • E4-4Audit lane for the outward direction: every client tool call is a flight-recorder event (mcp.host.*) — the external agent’s use of the sandbox is itself in the transcript, and kelyfos log --export renders the client lane alongside guest activity.
  • E4-5Client recipes: working config snippets for Claude Code and one more MCP client, added to the E3-3 cookbook and CI-executed like every recipe; make docs re-run so the generated reference and llms-full.txt pick up the new tools and toml keys automatically (F-D4 paying off).
  • E4-6Plugins drive (F-D6): the host packs each declared plugin’s files into a read-only ext4 image attached as the next virtio-blk drive, mounted at /plugins — ext4 rather than squashfs: both ride virtio-blk equally well (no loop device involved — /dev/vdc is already a block device), but squashfs would require adding CONFIG_SQUASHFS to the P1-2 kernel fragments, a config change for marginal gain (F-D6). Sizing per the P3-10 rule; image creation reuses the P3-10 workspace-packing mechanism (host-side mkfs.ext4 + populate — on macOS that runs inside the Lima VM, like all Linux work), pointed at the plugin files. Flavors may additionally ship built-in servers; both routes launch identically.
  • E4-7Supervisor plugin runtime: launch each [[plugin]] entry as a child process, speak MCP stdio to it, aggregate its tools into the agent’s session under the <plugin>.<tool> namespace. Per-call audit events carry the plugin name; a crashing plugin fails its own tools cleanly (plugin.crash event) without taking the supervisor down. Plugins get no egress of their own — the per-agent allowlist is the only network policy.
  • E4-8Proof, both directions at once: a scripted MCP client (CI) plus a live Claude Code session (demo) drive serve-mcp; inside the sandbox a small demo plugin shipped in-repo as a test fixture provides namespaced tools the inner agent calls. The exported transcript shows both lanes — the outer agent’s sandbox calls and the inner agent’s plugin calls.

Acceptance test — recreate & verify

  1. A scripted stdio MCP client connects to kelyfos serve-mcp, lists tools, and runs sandbox_run → sandbox_exec "uname -a" → guest kernel string returned.
  2. The client requests a sandbox with a domain outside the project toml → refused with the ceiling named, and the refusal is an mcp.host.* audit event.
  3. max_sandboxes + 1 concurrent sandbox_run → the extra one refused + audited.
  4. A sandbox with the in-repo demo plugin declared: team_peers-style listing shows the namespaced tools; calling one succeeds and the audit event names the plugin.
  5. Kill the plugin process inside the guest → its tools return clean errors, plugin.crash logged, sandbox_exec still works.
  6. kelyfos log --verify passes; --export renders the client lane and the plugin calls.
  7. Both E4-5 client recipes execute green in CI from a fresh clone.
  8. F-D9 exit requirements met: llms-full.txt regenerated with the new tools, token count re-measured and logged, and the E3-5 docs-only exam re-run against the MCP surface — transcript committed.

Exit checkpoint: tag v0.7 — “any MCP client can drive KelyfOS; any MCP server can run inside it.”

Epic E5 — Daily-driver QoL (v0.8)

QUEUED

Goal: remove every friction a developer hits daily once they already use KelyfOS. Eight small features that promote together: named pause/resume, diff + review-before-sync, an interactive shell, actionable denials, inbound port forwarding, run history with exact re-execution, desktop notifications, and a plain-text log tail. Two stances were written at promotion time (the parking condition for port forwarding): F-D7 — inbound exists only as explicit, loopback-bound, audited vsock-tunneled forwards, so the network-layer “no inbound path” invariant survives; F-D8 — interactive shell contents are not captured by default, --transcript opts in. Estimate: 3–4 weekends (the shell PTY and port forwarding carry the substance; the rest are wrappers over existing machinery).

  • E5-0docs/qol.md — spec first for the pieces that need shape: session-store layout (~/.kelyfos/sessions/<name>/ holding memory + disk snapshots, the workspace image, and a frozen copy of the policy toml); the workspace-manifest format for diff (path, mode, size, content hash); the PTY channel added to docs/protocol.md as an additive revision (raw stream + resize events); and the new audit event types (session.pause/resume, shell.start/end, forward.accept, run.review).
  • E5-1Named sessions: kelyfos pause [--as <name>] = P3-1 snapshot + teardown + store; resume <name> restores memory, disks, and the frozen policy — if the project toml changed since pause, warn and use the frozen copy (resumed VMs run under the policy they were paused with). Workspace sync-back happens at final shutdown after resume, never at pause. kelyfos sessions lists name/age/size; sessions rm deletes.
  • E5-2kelyfos diff + run --review: the P3-10 packing step records the manifest for free; at shutdown the guest tree is compared against it and rendered as A/M/D with numstat. With --review, the summary prints and sync-back waits for confirmation — decline routes results to the existing .kelyfos-out fallback (P3-10’s mechanism, reused), so the host directory is untouched until an explicit yes. The decision is a run.review audit event.
  • E5-3kelyfos shell: interactive PTY over the existing vsock channel — supervisor allocates the PTY, spawns the flavor’s shell, raw-mode passthrough with window-resize forwarding. Audit per F-D8: shell.start/end with duration always; contents only with --transcript, which stores the full terminal stream beside the session log.
  • E5-4Actionable denials, everywhere: every refusal (egress deny, unbound secret, resource ceiling, team edge, spawn budget, forward attempt) carries a structured error with a human fix line — blocked: api.stripe.com — add allow = ["api.stripe.com"] to kelyfos.toml, or rerun with --allow api.stripe.com. One error catalog in the docs; the E3 generated reference picks it up automatically.
  • E5-5Inbound port forwarding per F-D7: -p host:guest (repeatable) and [[forward]] toml entries. Host listener binds 127.0.0.1 only; --p-bind 0.0.0.0 is the explicit, loudly-warned LAN exposure. Transport is a vsock bridge (host listener ↔ supervisor ↔ guest-local port), so TAP and nftables stay egress-only and the network-layer no-inbound invariant holds. Every accepted connection is a forward.accept event with peer address; teardown closes all listeners.
  • E5-6Run history: a local index built from the session logs that already exist — kelyfos runs (id, time, image, command, exit, duration), kelyfos rerun <id> re-executing with the recorded image, frozen policy, and command, printing a provenance line. Plus kelyfos logs -f: the plain-text live tail of the flight recorder — the greppable sibling of watch.
  • E5-7--notify (flag + toml key): desktop notification on finish, block, timeout, or a waiting --review prompt — osascript on macOS, notify-send on Linux, terminal bell fallback — carrying exit status and duration.

Acceptance test — recreate & verify

  1. Write a file into guest scratch (tmpfs), kelyfos pause --as t1, kill every kelyfos process, kelyfos resume t1 → the scratch file is still there — full-state resume proven.
  2. Edit the project toml while t1 is paused → resume warns and runs under the frozen policy.

Why this answer: systemd-run --user --scope -p CPUQuota= performs exactly that move through the user manager, which is the one component that legitimately holds the privilege — and it sets the same cpu.max with the same 100 ms period. Requiring root instead would make a resource cap a privileged feature of a tool whose whole point is running unprivileged on a developer's machine. The applied cpu.max is read back and verified; a sandbox whose quota did not land refuses to start rather than running uncapped while claiming a cap. That check earned itself immediately — it caught the systemd move being asynchronous, which a write-and-hope implementation would have shipped as a silent hole.
