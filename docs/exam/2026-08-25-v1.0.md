# The v1.0 documentation exam

*P6-19. Three readers were given the `kelyfos` binary built from the commit under
test, `llms-full.txt`, and nothing else — no source tree, no `docs/` directory, no
`README.md`, no plan files, no git history, no web. E3-5's bar, and the environment
is what makes it evidence rather than theatre.*

*Date: 2026-08-25. Tasks chosen against the surface Phase 6 added, which is what E4
and E5 both did, rather than repeated for comparability.*

---

## What it cost, in one line

**24 findings survived adjudication, out of 28 reported.** Every finding was
re-read by somebody who *could* see the whole repository, whose job was to reject
anything the documentation actually says and the reader merely missed. Four were
rejected on exactly those grounds and are listed at the bottom, because a reader
who misses something findable is also a result — it means the page is hard to find,
not wrong, and those are different repairs.

| reader | finished the task | findings kept |
| --- | --- | --- |
| Trusting a report somebody sent you | yes | 8 |
| Attaching a client, and proving it works | yes | 7 |
| Upgrading from v0.9 | **no** | 9 |

**The one that matters most is a trust defect, and it is in v1.0's own new work.**
The exported report prints the signing key's fingerprint and tells the reader it
means something only if they recognise it from somewhere other than the page. That
fingerprint is the one value on the page a reader is instructed to act on, and it is
the one value `kelyfos verify` does not check. It is written up first below.

## Trusting a report somebody sent you

*macOS, no Linux, no KVM, no guest — the machine a report is most often sent to. Task completed.*

### 1. lets-you-overclaim

The report's banner states "Signed by the key whose fingerprint is 2087ffafa8f174b3..." and tells the reader it "means something only if you recognise the fingerprint from somewhere other than this page." But `kelyfos verify` does not check that fingerprint against the actual signing key. I replaced it with `deadbeef...` and verify reported "the values the page prints about this record agree with it" and exited 0 — including when `--key` named the correct key. Deleting the `id="kelyfos-fingerprint"` marker also passes, unlike the other three markers which fail closed. The word "fingerprint" appears 6 times in llms-full.txt and never once in reference to the report's signing key.

**Where:** docs/events.md §2 (Tamper evidence) and §5 (Reading the file) enumerate exactly three checked values — chain head, event count, session id. The fingerprint is a fourth trust-bearing value the export renders, is documented nowhere, and is unchecked.

**What it cost:** This is the one value the page instructs the reader to act on, and it is the one value verification ignores. A forger can display the fingerprint of a key the reader genuinely trusts while signing with an unrelated key, and `kelyfos verify --key <the trusted key>` still prints a fully clean result. I had to discover the gap by fuzzing the page's fields one at a time rather than by reading anything.

### 2. missing

The docs never state how the report's displayed fingerprint relates to the key `--key` and verify's output use. verify prints the key as raw hex (`6adc4af5...`); the page prints `2087ffaf...`. Nothing says the second is sha256 of the first's raw bytes. I established the relation by guessing and testing sha256(binascii.unhexlify(key)).

**Where:** docs/events.md §2; the `kelyfos verify` help text; the reference table for `--key` ("a PEM file, or the key in hex").

**What it cost:** A recipient literally cannot cross-check the page's banner against verify's output using the documentation alone — the two are in different encodings with no documented bridge. This compounds the finding above: even a careful reader who wanted to check the fingerprint manually has no documented way to.

### 3. lets-you-overclaim

`file.write` is defined as "A file was written through a tool" — i.e. via write_file/upload/serve-mcp/shim. The consequence is never stated: an ordinary shell redirect inside the guest produces no event, so the export's summary card can read "0 FILES WRITTEN" for a session that demonstrably wrote a file. The received report is a live instance: the recorded command is `echo audit-me > /work/n.txt; cat /work/n.txt` with stdout `audit-me`, and the card says 0. The report footer's "Every command, file write and network attempt the host observed is in that record" rests entirely on the unemphasised hedge "the host observed"; the card carries no hedge at all.

**Where:** docs/events.md §4 `file.write`; the export's summary cards; the export footer.

**What it cost:** I initially read "0 files written" as a substantive finding about the session and had to catch myself — the recorded command contradicted the card. Any reader treating the cards as an audit summary will conclude nothing was written when something was. Same reasoning silently applies to the 'egress allowed/blocked' cards and the byte counters.

### 4. missing

The docs specify the chain preimage precisely enough to reimplement ("recomputes the digest from the line as written, with the value of `hash` replaced by `""` in place") but for the signature say only that it is "ed25519 over the chain head and a digest of the record" / "covers the chain head and a digest of the whole record". No preimage construction is given.

**Where:** docs/events.md §2 ("What is signed is the record, not the page") and §5.

**What it cost:** I reproduced the hash chain independently on the first attempt, but could not verify the signature at all: nine plausible preimage constructions tested with openssl (sanity-checked against a self-generated key) all failed. This directly undercuts the repeated claim that verification needs "no server, no key, no network, and nothing on their machine has to have run" — that holds for the chain and not for the signature, and the docs do not distinguish the two.

### 5. misleading

The cookbook and the report both give `sed -n '/<pre id="kelyfos-chain">/,/<\/pre>/p' report.html | sed '1d;$d' | base64 -d > events.jsonl` and assert "what comes out is the record the sender has on disk, byte for byte." On a file carrying two `<pre id="kelyfos-chain">` blocks, `kelyfos verify` correctly refuses ("this file carries 2 embedded records; a report carries one") but the shell one-liner silently emits the attacker's decoy record, which then verifies clean as a standalone file.

**Where:** docs/cookbook.md recipe 6; docs/events.md §5; the report's own <pre class="howto"> block.

**What it cost:** The two extraction routes are presented as interchangeable and are not equivalent under adversarial input. The one-liner exits non-zero, but the cookbook's own worked example never checks the status, and in that pipeline the status belongs to `base64`. A recipient following the documented no-KelyfOS path gets forged evidence with no usable warning.

### 6. missing

`kelyfos verify` refuses a file carrying more than one embedded record — correct, fail-closed behaviour — but this check is documented nowhere.

**Where:** docs/events.md §5 "What it checks, exactly" lists the record's digests/ordering and the three page-level values; multiplicity is not mentioned.

**What it cost:** Low direct cost (the behaviour is safe), but it is the check that makes finding 5 above asymmetric, and a reader auditing what protection they have cannot know it exists. I found it only by trying the attack.

### 7. misleading

The export page says "The two numbers above are checked against the record too", but three values are checked — session id, event count and chain head. docs/events.md §5 gets this right ("the three values the page states about that record"); the page understates its own guarantee.

**Where:** the export's `.chain .limit` banner text vs docs/events.md §5.

**What it cost:** Minor and in the safe direction, but it cost me a test to discover the session id was also enforced, and it means page and docs disagree about the size of the checked set — which matters when the exact boundary of that set is the whole question.

### 8. hard-to-find

docs/events.md §2 defines the preimage as "the line as written, with the value of `hash` replaced by `""` in place" but does not say whether the trailing newline is included.

**Where:** docs/events.md §2, Tamper evidence.

**What it cost:** Very small — I guessed newline-excluded and it worked first try — but an independent implementer has a coin-flip to resolve, and the section is explicitly addressed to "where an independent implementation must take it from".

## Attaching a client, and proving it works

*Inside the Linux layer, with KVM. Task completed.*

### 1. lets-you-overclaim

Cookbook recipe 9's `check.py` — the documentation's own proof that a client configuration is right — passes against a `serve-mcp` running with NO policy and no ceiling at all. Both assertions fail to do their job. (a) `assert "kelyfos.toml" in init["instructions"], "the agent is not told where the wall is"` passes because the no-policy instructions read "No kelyfos.toml was found from where this server was started" — the substring is present precisely when the wall is absent. (b) `assert refused["isError"], "a request above the ceiling was granted"` passes for an unrelated reason: with no policy the default image is `base`, which was not installed, so the refusal was "sandbox_run: requested --image base but ... holds the "dev" image" — not a ceiling refusal, and naming no file and no line, directly contradicting the comment above it ("the refusal comes before anything is built, and it names the file and the line it came from"). The recipe prints a clean pass, and the reader concludes the wall is in place.

**Where:** docs/cookbook.md §9 "Point an MCP client at KelyfOS", the `check.py` heredoc

**What it cost:** I ran the documented check first and it reported success — 12 tools, a refusal, a clean exit. Had I stopped there I would have reported "attachment verified, policy enforced" about a server that then granted the same client a 6-vCPU, 2 GiB machine with egress to evil.example.com. It took a deliberate adversarial re-run against a policy-less server to catch it. This is the exact trap the surrounding prose warns about at length ('a client launched from somewhere outside the project would find no policy and run with no ceiling at all'), and the check written to catch it does not catch it.

### 2. lets-you-overclaim

"When the server exits, every sandbox it created is stopped. A client that disconnects without calling `sandbox_stop` does not leave microVMs behind." Stated unconditionally. It holds for a graceful exit (I verified: stdin close → server exits 0, firecracker count 2→1, `session end shutdown` written), but not when the server is killed hard. SIGKILL leaves a running firecracker process, an unowned microVM, and a record that stops at `ready` with no `session.end`. Nothing on the page distinguishes the two cases, and a force-quit or crashed client is the realistic version of "disconnects".

**Where:** docs/mcp-surface.md §2.3 "Sessions, concurrency and max_sandboxes", last paragraph

**What it cost:** I would have written "no cleanup risk" into my answer on the strength of the sentence. Testing it cost one deliberate SIGKILL and left a microVM I then could not shut down by any documented means (see next finding).

### 3. misleading

The `mcp.host.result` audit lane cannot distinguish a policy refusal from a command that merely exited non-zero. `sandbox_exec` running `exit 3` is recorded as `outcome:"error", error:{kind:"tool", message:""}` and replayed as `client result sandbox_exec refused: (15 ms)` — the word "refused", with an empty reason. §2.5 says "a refused call is drawn like a refused message, because it is the same thing: the wall saying no, where a reader can see it", which invites the reader to treat every such line as the wall. Separately, docs/reference/events.md documents `error` as "`kind` and `message`" for this event type but never enumerates the values `kind` takes — unlike the guest protocol §4, which enumerates bad_request/not_found/denied/timeout/killed. There is no documented way to tell the two apart from the record.

**Where:** docs/mcp-surface.md §2.5 "The audit lane"; docs/events.md and docs/reference/events.md, `mcp.host.call` and `mcp.host.result`

**What it cost:** Reading my own replay I counted three refusals and had to drop to `--json` to discover the third was a command that exited 3. It also undercuts the strongest claim the audit lane exists to support: neither "the record shows no refusals" nor "the record shows N refusals" is a statement a reader can make from the replay.

### 4. misleading

`kelyfos log --list` renders timestamps in local time while `kelyfos log --session` renders the same events in UTC, and neither output carries a timezone marker. The same session appeared as 16:02:29 in the listing and 13:02:27 in the replay. The schema documents the stored field correctly ("`ts` | string | RFC 3339 with milliseconds, UTC, host clock") but no page says how either renderer displays it.

**Where:** docs/events.md §3 "Common fields" and §5 "Reading the file"; docs/reference/cli.md, `kelyfos log`

**What it cost:** I briefly believed `--list` and `--session` were showing me two different sessions and re-checked the session id before working out the machine's timezone was EEST. For anyone correlating an exported report against a listing, or against an external incident timeline, the three-hour offset is silent.

### 5. missing

An `egress.attempt` event can be written after the command that caused it has already exited, so in a replay it appears underneath the *following* command. In my record `egress allowed api.github.com:443` is timestamped 13 ms after the `exit 0` of the curl that caused it, and therefore renders below the line for the next, unrelated curl. The docs say events are written "in the order the host observed them" and "the `ts` field is what orders them for a reader" — both true — but nothing warns that an egress event may not sit under its own command, which is the reading every reader will take.

**Where:** docs/events.md §1 ("in the order the host observed them"), §6, and the `egress.attempt` type

**What it cost:** Reading back my own egress proof, the record appeared to say the blocked-domain command had also made an allowed connection. I had to compare millisecond timestamps against the command boundaries to attribute it correctly — on the one artifact whose whole purpose was to be handed to someone else as evidence.

### 6. wrong

The two documented shapes of the same client's config disagree. Cookbook recipe 9 writes `.mcp.json` for Claude Code with `"type": "stdio"`; `kelyfos connect claude-code` (recipe 9b, the command the docs recommend over hand-editing) writes an entry with no `type` key at all. Nothing on either page says whether `type` is optional, defaulted, or required by that client.

**Where:** docs/cookbook.md §9 vs §9b; README "Attaching an agent" (which also shows the `"type": "stdio"` form)

**What it cost:** Low. I diffed the two and could not tell from the documentation which is authoritative, so I could not tell whether `connect`'s output is a bug or the hand-written form is redundant. It leaves a reader unable to check `connect`'s output against the documented shape.

### 7. hard-to-find

The single reliable over-the-wire way to tell a policy-bound server from a policy-less one — that `initialize.instructions` names the *absolute path* of the policy file in force — is stated only as prose ("The `initialize` instructions name the policy in force, or say plainly that none was found") and is never turned into a check a reader can copy. The one place a reader looks for such a check, the cookbook, gets it wrong (finding 1). Given how hard §1 and §2.3 press that a policy-less server is the failure mode to fear, the absence of the correct assertion is conspicuous.

**Where:** docs/mcp-surface.md §1 "The invariant" and §2.3; docs/cookbook.md §9

**What it cost:** I had to derive the discriminator myself by diffing the instructions text of a policy-bound server against a policy-less one, then confirm the absolute path was present in one and absent in the other. That derivation is the whole difference between a proof that means something and the cookbook's, which does not.

## Upgrading from v0.9

*Inside the Linux layer, with KVM. Task **not completed**.*

### 1. missing

docs/upgrading.md — the page whose stated purpose is "what breaks between versions and what to do about it" — contains nothing actionable for a v0.9 user. §1 covers snapshots taken *before* v0.9; §2 ("Writes outside /work, /tmp, /run and $HOME are refused") and §3 (ptrace) are both "Since v0.9"; §4 says "Nothing to do"; §5 is "What has never broken". It is a page about upgrading TO v0.9, shipped in a documentation set describing the version after v0.9. Its own preamble even says "Everything below predates that promise" without noticing that everything below also predates the reader.

**Where:** docs/upgrading.md, whole page

**What it cost:** I read the one page that should have been the entire answer and came away believing almost nothing would break. Every real item in my final list came from grepping 'v1.0' across nine other documents afterwards. If I had trusted the page — which is exactly what a competent stranger does with a page called Upgrading — I would have upgraded and silently lost workspace data.

### 2. hard-to-find

The workspace write-back validation — the whole ext4 image refused if any entry is a socket, fifo, device node, an absolute or climbing symlink, or a name containing a separator/NUL/control character/'.'/'..' — is documented only in README's security table and threat-model.md §4 "The workspace disk, which this table did not list", both framed as a *security improvement*. It appears nowhere in upgrading.md. README even says "It closed on `main` after v0.9 was tagged", so the docs know it is a v0.9→next break and still do not list it as one.

**Where:** README.md §Security; docs/threat-model.md §4; absent from docs/upgrading.md

**What it cost:** The single most likely thing to break a real user's setup is filed under 'what we hardened', not under 'what will break'. A Python venv or a leftover unix socket in the workspace is enough to trigger it, and I only went looking because I was grepping for version strings rather than reading for meaning.

### 3. lets-you-overclaim

Nothing anywhere documents the consequences of that refusal. Verified by experiment: `kelyfos run --workspace … -- <cmd>` prints `kelyfos: workspace sync-back failed: …` to stderr, leaves the host directory untouched, discards everything the agent wrote, writes no `<dir>.kelyfos-previous`, **exits 0**, and writes no event to the flight recorder (`session.end` reads `code: 0`). The cookbook's own promise for this form is "exits with the command's own status, so it composes in a script", with no caveat.

**Where:** docs/cookbook.md recipe 3; docs/integrating.md §6; absent everywhere

**What it cost:** I had to run the binary to learn this; no document says it. It defeats the pattern integrating.md itself recommends — 'Read the record rather than the output' — because the record does not contain the loss. A script doing `kelyfos run --workspace . -- agent && deploy` now deploys nothing and reports success.

### 4. misleading

The documentation set has no reliable version identity. The llms-full.txt header says "The release this describes is in the README's status block"; the README says "Status: v0.9"; the same README says the workspace fix "closed on `main` after v0.9 was tagged"; docs/README.md says "it is normative from v1.0 and this repository is at v0.9, so nothing in it binds yet"; and dozens of sentences across the set narrate "since v1.0" / "from v1.0" behaviour in the present tense as already shipped. The binary beside the documents reports `v0.9-55-gb68c629`.

**Where:** llms-full.txt header; README.md status block; docs/README.md §Inventory

**What it cost:** For every 'since v1.0' sentence I had to guess whether it described the version I run or the version I would upgrade to. That distinction is the whole task. I resolved it only by reading the binary's version string, which is not documentation.

### 5. missing

Several behaviour changes are dated only by internal task identifiers with no document mapping them to releases: `write_file`/`upload` confined to the profile's writable trees (P6-24), `[team.agent.spawn.resources] max_runtime`/`idle_timeout` refused rather than silently ignored (F-D33, F-D20), the shim's 16-sandbox ceiling, `file.write` recorded after the guest answers, and the `structuredContent` rule that made large `read_file` calls fail. The prose dates them as "could once", "used to parse and do nothing", "the policy carried a ceiling for each of those … and none for the number of machines".

**Where:** README.md security table; docs/hardening.md §5; docs/teams.md §3; docs/events.md §4 file.write; docs/e2b-shim.md; docs/mcp-surface.md §2.2

**What it cost:** Five potential breaks I could not place on either side of the upgrade line. I verified the team-file key refusal fires on the new binary (`F-D33`, exit 1, names the line) but still cannot tell a colleague whether it is new to them. I wasted a pass trying to infer release boundaries from P/F/E/D numbering before concluding no such mapping is published.

### 6. misleading

upgrading.md §2 states the writable-tree restriction as "Since v0.9" without noting that the supervisor's own `write_file` and `upload` MCP tools were exempt until after v0.9 — README says they "could once write anywhere the guest asked, including the block devices the profile withholds", and hardening.md attributes the fix to P6-24.

**Where:** docs/upgrading.md §2 vs README.md security table and docs/hardening.md §5

**What it cost:** A v0.9 reader concludes from §2 that they have already absorbed this break in full. Any setup step that used the MCP file tools to write outside /work,/tmp,/run,/root still works for them today and stops working after the upgrade.

### 7. hard-to-find

`kelyfos fork` beginning to read `kelyfos.toml` — a genuine, reproducible break — is documented in one sentence buried in resources.md under the heading "Seeing the limits hold", a section otherwise about `kelyfos watch`. reference/cli.md lists fork's `--policy` and `--cpu-quota` flags with no indication either is new.

**Where:** docs/resources.md §Seeing the limits hold; docs/reference/cli.md §kelyfos fork

**What it cost:** Verified break: `fork --cpu-quota 200` against a `cpu_quota = "50%"` ceiling now exits 1 with `[ceiling.flag]` where v0.9 ran it. Anyone reading the fork recipe in the cookbook or the fork entry in the CLI reference — the two places you would look — learns nothing about it.

### 8. wrong

`--secret`'s own `-h` output and docs/reference/cli.md both give the spec as `NAME@domain[:bearer|basic]`, omitting the `/path` endpoint-binding form that networking.md §6 and reference/config.md document as the way to bind a credential to one endpoint. reference/cli.md is generated from the binary's usage and is one of the seven surfaces compatibility.md §2 pins.

**Where:** docs/reference/cli.md §kelyfos run; the binary's `run -h`

**What it cost:** A new capability worth adopting during the upgrade is invisible from the two places a CLI user looks. The generated-and-drift-checked reference is accurate about the string the flag prints and wrong about the grammar the flag accepts, which is a failure mode the generation story ('a flag in the reference cannot be one that no longer exists') does not cover.

### 9. missing

docs/teams.md §4 says "Writing an empty value removes the key. That is the only way to make the store smaller, and until v1.0 there was none" — but never states what writing an empty value did before, so a reader cannot tell whether `put(key, "")` previously stored an empty value that `get` returned.

**Where:** docs/teams.md §4

**What it cost:** A silent semantic change I can flag as a risk but cannot confirm. Any agent using an empty value as an 'exists but empty' sentinel would flip from returning "" to returning `not_found`, and the documentation gives me no way to tell a colleague whether to worry.
