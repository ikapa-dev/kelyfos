## F-D1

*2026-08-22*

No GPU support on the Firecracker backend — permanently, not “yet”. Firecracker offers no device passthrough; its minimal device model *is* the security posture. GPU work is possible only via an alternate VMM backend and stays in the parking lot until promoted as its own epic.

**Evidence:** States the physics up front so nobody burns a weekend discovering it. Stated here independently so it holds regardless of which PLAN.html revision is running (see E1-0).

## F-D2

*2026-08-22*

All resource caps enforce **host-side only**: KVM machine config, cgroup v2, Firecracker rate limiters, tmpfs mount options, device sizes, host timers. Nothing inside the guest is trusted to police itself.

**Evidence:** The guest runs untrusted agent code — guest-side limits are advisory at best and theater at worst. Same trust model as the P2-5 egress design (proxy on the host, not a guest firewall).

## F-D3

*2026-08-22*

Non-goal renegotiated **by name**: the build plan’s “no orchestrator / control plane” non-goal is narrowed, not removed. **In scope now:** single-host, user-declared agent-team topologies — multiple KelyfOS VMs with edges enforced by a host-side broker, a permissioned team store, spawn-under-budget, and team-level resource hierarchies (Epic E2). **Still out, permanently:** multi-host scheduling, hosted control planes, autoscaling services, work queues as a product — the fleet layer where E2B/Kubernetes live.

**Evidence:** Proposed and approved by John, 2026-08-22 (this feature request *is* the renegotiation the parking lot required). The distinction: a fleet control plane manages infrastructure for you; a team topology is policy the user declares and KelyfOS enforces — networking + policy + audit, the product’s home turf. Orchestration *logic* stays in the agent framework; KelyfOS is mechanism.

## F-D4

*2026-08-22*

Documentation principle: the **reference is generated from the code** (CLI flags, toml keys, MCP schemas, event types, exit codes) and CI fails on drift; hand-written docs are reserved for concepts and recipes, and every recipe is executed in CI. The docs ship as `llms.txt` / `llms-full.txt` for machine readers.

**Evidence:** Docs that can lie are worse than no docs — for LLM consumers especially, a stale flag name produces confidently wrong code. Generation + CI makes staleness a build failure instead of a user bug report.

## F-D5

*2026-08-22*

Both MCP parking items promoted into Epic E4 per the §2 path. Standing invariants: (1) `serve-mcp` can never widen policy — the project’s `kelyfos.toml` is the ceiling and no MCP tool exists to modify it; policy changes stay human-only. (2) Plugin tools are namespaced `<plugin>.<tool>`. (3) In-guest plugins get no egress of their own — the per-agent allowlist is the single network policy surface.

**Evidence:** Approved by John, 2026-08-22. The outward server is the highest-leverage adoption path (every MCP client becomes a user with one config line); the inward slot is what “MCP-native” structurally implies. Plugins are safe to allow because they run inside the same isolation — a malicious plugin has exactly a malicious agent’s powers, which the sandbox already assumes.

## F-D6

*2026-08-22*

Plugin delivery: injected at boot via a host-packed **read-only ext4 plugins drive** (next virtio-blk device, mounted at `/plugins`), sized per the P3-10 rule. Flavors may also bake servers in; both routes launch through the same supervisor runtime. ext4 chosen over squashfs to leave the P1-2 kernel fragments untouched.

**Evidence:** Per-project plugin sets are the point — baking-only would force an image rebuild per plugin change and bloat the 5 MB base. Read-only device + same-isolation containment keeps the trust story identical to the rootfs. Squashfs would be smaller but adds a kernel config change for marginal gain.

## F-D7

*2026-08-22*

Inbound stance (the port-forwarding parking condition, written at promotion): forwards exist only as explicit per-run `-p` flags or `[[forward]]` toml entries; host listeners bind loopback by default with LAN exposure a separate, loudly-warned flag; transport is a vsock bridge so TAP/nftables remain egress-only and the network-layer no-inbound invariant is preserved; every accepted connection is audited; teardown closes all listeners.

**Evidence:** Approved by John, 2026-08-22. The most-requested sandbox feature must never mean “the sandbox is silently reachable”: inbound rides the already-trusted host channel, is user-declared per run, and leaves an audit trail like everything else.

## F-D8

*2026-08-22*

Interactive-shell audit stance: `kelyfos shell` logs `shell.start/end` with duration always; terminal *contents* are captured only with an explicit `--transcript` flag.

**Evidence:** A human typing into a shell is not an agent acting — capturing keystrokes by default is surveillance, not audit. The audit chain still shows that a human entered the sandbox and for how long; full capture stays one flag away for regulated use.

## F-D9

*2026-08-22*

**Docs ride with features.** From E3’s exit onward, every epic’s exit checkpoint additionally requires: clean `make docs`; `llms.txt`/`llms-full.txt` regenerated and committed with the epic; a CI-executed cookbook recipe for each new user-facing command, flag, toml key, or MCP tool; the llms-full.txt token count re-measured and logged; and a re-run of the E3-5 docs-only exam (transcript committed) whenever the epic added commands or MCP tools. Encoded as protocol rule 4 in §2 and as explicit acceptance lines in E4 and E5.

**Evidence:** Approved by John, 2026-08-22. For an LLM consumer, docs lagging one feature behind are worse than missing docs — the consuming agent confidently writes around features that exist. Generated parts are already enforced by CI drift-failure (F-D4); this closes the hand-written half and makes “updated” mean *proven usable*, with the docs-only exam as the standard of proof.

## F-D10

*2026-08-22*

The resource knobs E1-0 goes looking for shipped **partly**: `--vcpus`/`--mem` and `[sandbox] vcpus`/`mem_mib` are real and effective in v0.3, but `--disk` and a `[resources]` section never existed. The missing half is implemented here and therefore ships in **v0.4, not v0.1**. Two naming facts are settled now so later tasks do not trip on them: the flag the epic calls `--cpus` exists in this build as `--vcpus`, so `--cpus` becomes the documented name with `--vcpus` kept as a working alias rather than a rename that would break the v0.3 CLI a day after release; and `[sandbox] mem_mib` stays valid alongside the new `[resources] mem` for the same reason. E1-0 deliberately stops at making the knobs exist — precedence stays v0.3 behaviour (a flag overrides the file) because turning the file into a **hard ceiling** is E1-1's spec-before-code job, and pre-empting it here would be exactly the deviation the protocol forbids.

**Evidence:** boot test in the E1-0 progress row

## F-D11

*2026-08-22*

E1-2's CPU quota is applied by **asking systemd for the scope** when KelyfOS is running unprivileged under a systemd user session, and by writing `cpu.max` directly only when it actually can. The percentage→`cpu.max` mapping E1-2 specifies is unchanged and still done in the CLI: `"150%"` is `150000 100000`, and the resulting file is **read back and verified** after launch rather than assumed. *Why the change:* the task says “launch each Firecracker process inside its own cgroup v2 slice”, and writing that cgroup ourselves turns out to be impossible unprivileged, for a reason that is a property of cgroup v2 rather than a bug to work around. A login session lives in `session-N.scope`, which is root-owned; the subtree systemd delegates to the user is `user@UID.service`. Moving a process between them needs write access to the **common ancestor**'s `cgroup.procs` — `user-UID.slice`, owned by root. So the target directory being ours is not enough, and `clone3(CLONE_INTO_CGROUP)` fails with a bare `EACCES` that surfaces as “fork/exec: permission denied”. Confirmed directly: we can `mkdir` under the delegated subtree and write its `cpu.max`, and still cannot put a process there. *Why this answer:* `systemd-run --user --scope -p CPUQuota=` performs exactly that move through the user manager, which is the one component that legitimately holds the privilege — and it sets the same `cpu.max` with the same 100 ms period. Requiring root instead would make a resource cap a privileged feature of a tool whose whole point is running unprivileged on a developer's machine. The direct path is kept for root and for containers where the root cgroup is genuinely delegated, so CI and rootless-container hosts do not depend on systemd; when neither is available the flag refuses with the reason rather than pretending to cap anything.

**Evidence:** probe output in the E1-2 progress row

## F-D12

*2026-08-23*

PID 1 exempts itself from the guest OOM killer (`oom_score_adj = -1000`), and the supervisor writes `0` to every child's `oom_score_adj` immediately after starting it. Both halves are required; neither is optional and neither may be simplified away.

**Evidence:** The first half is not the guest policing itself, which F-D2 forbids — it limits nothing, and the RAM cap is the VM's hardware either way. It is about surviving long enough to report: killing PID 1 is a kernel panic, so a supervisor the OOM killer may choose turns "the agent was killed for using 224 MiB of a 256 MiB machine" into "the sandbox vanished", which is the exact outcome E1-4 exists to remove. The second half is the trap, found by running it: `oom_score_adj` is **inherited across fork**, so the exemption alone makes every process in the guest unkillable and the kernel prints "Out of memory and no killable processes" instead of naming a victim. Measured directly — a guest that had correctly killed one Python process before the exemption produced no OOM event at all after it, and no kill line on the console either. Restoring the score per child costs one small write and leaves a window between fork and that write; the window is an exec long, and a command that reads its own `oom_score_adj` as its very first act already reads 0.

## F-D13

*2026-08-23*

`scratch` is applied by the **guest** kernel, as a `size=` on the tmpfs it mounts, and this is stated as an exception to F-D2 rather than filed under it. The cap is a partition of a budget the host has already fixed, not a boundary of its own.

**Evidence:** F-D2 says every cap enforces host-side, and every other one in this epic does. A tmpfs's size cannot: it is by construction a property of the kernel that mounts the filesystem, and inside a microVM that kernel is the guest's. A guest determined to defeat the cap can remount with a larger size — and gains nothing at all by it, because the tmpfs lives in guest RAM and `mem` is the VM's hardware. So the honest description is the one written into `docs/resources.md`: `scratch` stops an agent filling its own memory with build output by accident, and is not a defence against one trying to. Recording it as an exception rather than quietly counting it as enforcement is the point — a limit whose actual strength is misunderstood is worse than one whose weakness is written down. The number itself travels on the kernel command line, which the guest cannot alter, and a `scratch` above `mem` is refused at boot instead of accepted as an unreachable limit.

## F-D14

*2026-08-23*

The E1-7 resources lane in `kelyfos watch` reads host counters — cgroup `cpu.stat`, `/proc/<pid>`, the TAP's byte counters — alongside the flight recorder, which PLAN.html's D7 describes as the only thing monitoring may read. The durable record is unchanged: exactly one `resource.summary` per session, written at teardown.

**Evidence:** D7's own litmus test is “does it read the JSONL, or does it manage sandboxes? Readers are fine; managers are scope creep”, and a gauge that samples counters about a sandbox it is already watching manages nothing. The alternative considered and rejected was to emit a `resource.sample` event every second so the view could stay recorder-only: that would put roughly 3,600 events an hour into a tamper-evident log in order to draw a number that is stale a second later, which is a metrics store wearing an audit log's clothes. The distinction worth keeping is between a *reading* and a *record*. A live gauge is a reading and does not belong in the chain; the receipt is a record and does. Both come from the same host-side counters, so the lane and the receipt can never disagree about what happened.

## F-D15

*2026-08-23*

Team messaging gets a channel of its own, `team` on port 10102, running **guest → host**. It is not carried on any existing channel.

**Evidence:** E2-1 says “over the existing per-VM vsock channels” and this is that, in the only way the sentence can be satisfied: the same hybrid-vsock mechanism, per VM, one more port. Nothing already defined can carry it. `ready` and `events` run the right direction but are one-way reports with no reply path; `exec`, `mcp` and `control` all run the other way, because every one of them exists because the host wants something from the guest. This one exists because an agent inside a guest wants to reach another agent, which is a request the guest has to originate. The host is the only participant that can answer it: it is the only one holding the edge list, the other guests' channels, and the audit chain. A guest asks; a guest is never asked to route, and no guest ever receives a connection from another guest because there is no path for one.

## F-D16

*2026-08-23*

The `[team]` schema is read by **extending KelyfOS's own parser**, not by taking a TOML library. The parser gains array-of-tables (`[[team.agent]]`) and one level of nested table (`[team.agent.resources]`), and goes on refusing everything it does not recognise, by name and line. Revisit if the schema ever needs inline tables, dotted keys or datetimes: at that point the subset stops being a subset a person can hold in their head, and `github.com/BurntSushi/toml` is the one to take.

**Evidence:** Both alternatives were checked rather than assumed. `BurntSushi/toml v1.6.0` (2025-12-18, MIT, 5.0k stars, no transitive dependencies) and `pelletier/go-toml/v2 v2.4.3` (2026-07-05, MIT, 2.0k stars) are both current, both maintained, and either would parse this schema correctly today and every schema after it. The argument against is not their quality; it is what this particular file is. `kelyfos.toml` is *policy* — who may talk to whom, what may leave the network, which secrets exist. This project's whole pitch is that the policy is enforced and auditable, and for that job a parser a reader can audit in ten minutes is worth more than a general one nobody here will read. The usual objection to hand-rolling — that it will misparse something — is blunted by the rule the parser already follows everywhere: anything it does not understand is an error naming the line, never a silent skip. The failure mode is a refusal, not a misreading, and a refusal is the failure mode this project picks everywhere else. The cost is honest: every schema growth is parser work, and a user who writes valid TOML outside the subset is told no. That is the trade, and the condition for reversing it is written above rather than left to taste.

## F-D17

*2026-08-23*

`kelyfos team up` boots its agents as **concurrent cold boots**, not as forks from a shared snapshot. E2-4's parenthetical asks for the fork, and the fork is not available to a team as teams are specified. **The E2 acceptance test's “total spawn time < 1 s” bar therefore cannot be met by this implementation and will be reported as not met**, with the measured number, rather than quietly restated.

**Evidence:** The obstacle is P3-2 and D22 rather than effort. A fork is vsock-only by the build plan's own design: N forks would need N distinct guest network identities, and the guest's address and default route are baked into the memory image, so separating them genuinely needs a network namespace per fork — which D22 puts in P4-1 jailer territory. `kelyfos fork` already refuses a networked snapshot for exactly this reason. A team agent with an `allow` list needs a NIC, so fork-based spawn would work only for agents with no egress: a minority case, and a second boot path whose availability depends on a policy field. Two paths where one will do, for a case that is not the common one, is worse than one honest path and a recorded gap. What was done instead is real: the agents boot together rather than one after another, since nothing about the second depends on the first. On this dev machine that buys nothing measurable — three concurrent boots take 2.34 s against roughly 2.31 s sequential, because a nested guest with six vCPUs is CPU-bound long before it is latency-bound — and per D15 that is a fact about the measuring environment. The reference runner decides whether it buys anything, and the number goes in the log either way. Revisit when forks gain per-fork network identity. Until then the honest options are this, or a team whose agents may not reach the network, and the second is not a team anybody asked for.

## F-D18

*2026-08-23*

`team_spawn` is **listed** only for an agent whose policy granted a budget — the host says so on the kernel command line, as `kelyfos.spawn=1`, next to the agent's own name — but it is **refused** host-side, never guest-side. Advertising and enforcing are deliberately separated.

**Evidence:** Two rules pull in opposite directions and both are right. docs/teams.md §3.6: a tool that is always advertised and always fails teaches a model to ignore failures, so an agent with no budget should not see one. docs/teams.md §5: a spawn by an agent with no `team.spawn` at all is refused *and audited*, and a refusal the host never sees is a refusal that never reaches the log. Doing the check in the guest would satisfy the first and break the second. Splitting them satisfies both: the list is a hint, the host is the authority, and an agent that calls a tool it was never shown still produces a `team.spawn` refusal record. The flag rides the kernel command line for the same reason the agent's name does — it is the one thing inside the guest that the guest did not write, so a guest cannot grant itself a budget by asserting one.

## F-D19

*2026-08-23*

**Standing ruling from John, superseding F-D17’s “cannot be met” clause.** F-D17 stays in the log exactly as written and its honest-reporting stance stands; what changes is the scope of its conclusion. `kelyfos team up` gains a **fork fast path for exactly those agents whose policy grants no egress**. For each distinct image among the no-egress agents: boot one NIC-less template, snapshot it once, and fork the N workers from it, each with its own vsock endpoint through the `vsock_override` that P3-2 already passes (a per-sandbox UDS path in this implementation — the hybrid-vsock equivalent of the ruling’s “distinct CIDs”), with the per-fork entropy and clock resync D19 already requires. Agents that *were* granted egress continue to cold-boot concurrently, unchanged. No network-namespace work, no P4-1 dependency, no second network path — this is P3-2’s vsock-only fork used as designed. The E2 acceptance test’s “total spawn time < 1 s” bar is then **measured** on the bare-KVM reference (D15) rather than pre-declared: if it passes it passes; if it fails the measured number is reported as not met, with the reason. E2-5’s budgeted runtime spawns stay cold boots; if a spawn budget’s image whitelist ever contains no-egress images the same fast path may serve it later — a parking-lot item, not work.

**Evidence:** The ruling narrows F-D17’s claim rather than contradicting its evidence. Everything F-D17 measured is still true: a fork cannot carry a NIC, because the guest’s address and default route live inside the memory image every fork shares, and a team agent with an `allow` list needs a NIC. What it over-claimed is the conclusion. It treated a team as one population and argued that one honest path beats two — “a second boot path whose availability depends on a policy field” — when the population actually splits on a field the host reads from the toml *before it boots anything*. That is the difference between a runtime surprise and a plan-time fact, and it is the whole of the disagreement. The demo E2-9 asks for is the shape this serves: four workers that split a task, coordinate through the team store and talk only to their master need no network of their own, and the acceptance test says in its own words that they “spawn via fork”. Choosing the path per agent also keeps the divergence visible rather than hidden — which boot path each agent took is a fact about that agent, and it belongs in `team ps` and in the flight recorder like every other fact about it. The cost is honest and is F-D17’s cost, now paid deliberately: there are two boot paths in `team up`, and a team of egress-granted agents gets no benefit at all from this work.

## F-D20

*2026-08-23*

Inside a `[team]`, `[team.agent.resources] idle_timeout` is **refused at the file** — by name, by line, citing this decision and naming what to use instead. `max_runtime` is honoured per agent. The refusal lifts when E2-7 gives the team transcript a per-agent activity signal; until then the key does not exist for a team member.

**Evidence:** E1-6’s idle watchdog answers “has anything happened lately” from two host-side facts: the session’s flight-recorder file grew, and the egress proxy moved a byte. Both are properties of a *session*, and a team is deliberately *one* session — E2-1 chose one verifiable transcript over five that have to be correlated afterwards, and that choice is worth more than this key. So inside a team the first fact is a team-level signal: a busy master keeps an idle worker’s clock alive indefinitely, and the budget would be inert in precisely the case a user writes it for. Two alternatives were considered and rejected. Giving each agent its own recorder would make the timer work and would cost the single team transcript, which is a much larger promise to break for a much smaller feature. Filtering the shared log on the `agent` field is the right answer and is not available yet: an `exec` against a team member currently writes into that member’s own session file rather than the team’s, which is exactly what E2-7 exists to fix — so the mechanism is one task away rather than absent. Refusing is what the project does everywhere else with something it cannot enforce, and it is the opposite of what this task had to come back and fix: `allow`, `secrets` and `workspace` were accepted per agent and silently dropped for a release, which is the failure mode a refusal exists to prevent. `max_runtime` needs none of this — an agent’s wall clock starts when the host boots it, and the host is holding the clock.

## F-D21

*2026-08-23*

Three rulings E2-6 needed and the plan did not specify, taken together because they are one design. (1) **Schema**: the collective cap is `[team.resources] cpu_quota` — one new section, one key. A per-agent cap written there (`mem`, `cpus`, `disk`, the rates, the time budgets) is refused with a message saying where it belongs, separately from “unknown key”. (2) **The sum is not checked**: agents may oversubscribe the team, and only a *single* agent asking for more than the whole team is refused. (3) **No per-agent `weight` key** in E2-6: every child gets `cpu.weight = 100` and there is no way to write anything else. Additionally, on a systemd user session the parent’s cap is set with `systemctl --user set-property --runtime` *before the first agent starts*, not by writing the slice’s `cpu.max` by hand.

**Evidence:** (1) `cpu_quota` is the only cap a team can share, and that is a fact about the mechanism rather than a scoping choice: cores, RAM and disk are handed to each agent at boot as that machine’s hardware, and a parent cgroup cannot pool hardware. So `mem` at team level is not a typo, it is a wrong mental model, and F-D16’s whole promise is that the file tells you which. It also had to be a table bound to `[team]` rather than to an element above it, so that — unlike `[team.agent.resources]` — it may be written anywhere in the file. (2) Five agents at `100%` under a team cap of `200%` is not a mistake, it is the configuration worth writing: each may burst to its own ceiling while the others idle, and the parent holds the total. Refusing oversubscription would forbid the only reason a shared budget exists. The asymmetry is deliberate and is the same one `docs/resources.md` already draws about per-device disk limits: a *single* ceiling written above another ceiling and then ignored is a number a reader would go on to trust, so that one is refused. (3) A weight is not a cap, so `[team.agent.resources]` is the wrong home for it — that table is pinned key-for-key against a single run’s `[resources]` by a test, and a weight means nothing to a sandbox with no siblings. Equal weights are literally what E2-6’s “divides contention fairly” asks for. F-D16 prices every schema growth as parser work; if a declarable weight is wanted later it belongs on `[[team.agent]]` beside `count`, and that is a decision to take then. The systemd half was **measured, not assumed**. Writing the slice’s `cpu.max` directly is the obvious move and is wrong: systemd applies the unit’s own properties when it materialises a slice, so a value written into a directory systemd has not started yet is discarded — proved by writing `300000 100000` into a hand-made slice directory and watching the first scope reset it to `max`. `set-property --runtime` on a slice that has never existed returns 0, creates the slice *and every level above it*, and the cap is already in place when the first agent lands — so there is no window in which the team runs uncapped, which is the property the direct path has and the one worth matching. It needs `systemctl`, which is not a new dependency in any meaningful sense: it ships in the same package as the `systemd-run` this path already requires, and it is only reached when a collective cap was actually asked for.

## F-D22

*2026-08-23*

A sandbox carries the flight recorder it belongs to. `sandbox.json` gains a `session` field — empty for an ordinary run, the team’s session id for a team member — and `kelyfos exec` and `kelyfos mcp` open `State.RecordSession()` instead of the sandbox’s own id, stamping `agent` on everything they write. Two user-visible consequences, both deliberate: a team member has **no record of its own**, and `kelyfos log --session <agent id>` redirects to the team’s record and says so on stderr while that sandbox still exists.

**Evidence:** E2-7 asks for `--verify` to cover “the whole team chain”, and at the start of the task there was no such chain: `host/exec.go` and `host/mcp.go` opened `recorder.Open(root, st.ID)`, so every command run against a team member landed in that member’s own file while the messages that asked for the work landed in the team’s. The concurrency it leans on was already there and already tested — every `Append` takes an exclusive lock and re-reads the true tail, and `TestConcurrentWritersKeepOneChain` covers six writers against one chain. **One consequence for F-D20, recorded rather than acted on.** F-D20 refused per-agent `idle_timeout` and said the refusal lifts “when E2-7 gives the team transcript a per-agent activity signal”. ## F-D24

*2026-08-23*

Building F-D19’s fork fast path settled four things the ruling did not specify. (1) **What makes agents share a template**: everything baked into a memory image — image flavor, cores, RAM, scratch, the I/O rates, and whether the agent has a spawn budget. `cpu_quota` is deliberately excluded, because it is a host-side cgroup on the VMM process rather than anything inside the machine, so forks of one snapshot may hold different quotas and each gets its own slice at restore. (2) **A `workspace` disqualifies an agent from forking**, for a reason unrelated to networking: a fork copies the template’s disk, and the template’s disk is whichever agent’s directory was packed into it. (3) **A group of one cold-boots.** A template costs a boot and a snapshot, so forking a single agent is strictly slower than booting it; the saving starts at two. (4) **A fork is not told who it is by its own image**, and does not need to be. The host has always decided which agent a channel belongs to. The one place a guest still answered that question for itself — the `agent` field `team_peers` returns — now comes back from the host with the peers.

**Evidence:** The ruling was right that the obstacle is network identity and that a NIC-less agent has none. What it could not know from outside the code is that `Restore` was written for `kelyfos fork`, which restores machines that are nobody in particular: it bound no team channel, carried no agent name, no session, no cgroup. A forked team member with no team channel is a machine in a team that nothing can speak to, so the fast path is only available at all once `Restore` carries the same identity a cold boot does. That is the real work the ruling implied and did not name, and it is worth recording because it is the part a later reader would assume was free. The identity question looked like the blocker and was not. Every fork of one template carries that template’s kernel command line, `kelyfos.agent=` included — so on the first live run all four workers reported themselves as `worker-1`. Nothing about the team was actually wrong: the peers each one got back were its own, the messages routed correctly, the store rules held, because `broker.Serve` is called with the name the *host* bound to that machine’s channel and a guest’s opinion of its own name is never read off the wire. The defect was one echoed field, and the fix makes the host authoritative there too rather than teaching the guest to rename itself — which is the same stance as everywhere else: the guest is told things it cannot verify, and asserts nothing the host will believe. The exclusions are deliberately conservative. Forking is an optimisation, and an optimisation that quietly hands one agent another’s files or another’s spawn budget would be paying for milliseconds with the product’s only real claim.

## F-D25

*2026-08-23*

Measured on the reference: **the fork fast path costs more than it saves there, and it is what makes the E2 spawn bar unmeetable.** Total spawn on the bare-KVM runner is **1098 ms** against a 1000 ms bar — missed by 98 ms — and 927 ms of it is the one-time write of the template’s memory image. A cold boot on that same machine is 109–134 ms. Five concurrent cold boots would therefore have come in far under the bar, and the fork path is the reason it is missed. The path stays as F-D19 ruled and as E2-9 built it; what is recorded here is the number, the comparison, and the open question, which is John’s to answer because it revises F-D19’s premise rather than its implementation.

**Evidence:** F-D19’s reasoning was that concurrent cold boots could not meet a sub-second bar and that forking would. That was sound on the evidence available: on the nested dev machine a cold boot is ~2.2 s and a fork ~0.4 s, so forking four workers is the difference between 2.2 s and 1.8 s and the bar is out of reach either way. The reference environment inverts it, because the two costs scale differently. A cold boot is CPU and device setup, and that runner is fast at both: 109 ms. A fork is one memory-image write plus N cheap restores, and that runner is *slow* at the write: 927 ms for 384 MiB, about 220 MB/s. The dev machine’s NVMe does the same write in 151 ms. So the ratio that makes forking pay reverses between the two machines, and the environment D15 makes binding is the one where it does not pay. Reported rather than buried because the alternative is the flattering omission: it would have been easy to write “1098 ms, not met, the memory write dominates” and leave out that not forking at all would have met it. F-D19 asked for the measured number with the reason; the reason is the fast path. Three things follow, none of them taken here. (1) The fast path is not wrong — it is a large win where boot is expensive, which is every nested host and every machine with a slow CPU and a fast disk. (2) The obvious repair is to stop paying the write per `team up`: a template snapshot keyed on the image and machine shape could be cached between runs, turning 927 ms into a first-run cost. That needs a decision about invalidation — an image rebuild must not be servable from a stale template — and it is parked, not designed. (3) Choosing per host by measurement rather than by rule would be the other answer, and a heuristic that guesses which of two costs is larger without measuring either is how a fast path becomes a slow one silently. Neither is E2’s to decide.

## F-D26

*2026-08-23*

**Ruling from John on F-D25, superseding F-D19’s fork mandate. Both stay in the log untouched; this replaces the strategy, not the record.** Team-up becomes **cold-first, fork-warm**: **(1)** with no cached template, *every* agent boots as a concurrent cold boot — the measured 109–134 ms path, and the path the < 1 s bar binds on. **(2)** Once a template for a given (image digest, memory size, guest configuration) has been created, its snapshot is cached; a later team-up that hits the cache forks its NIC-less no-egress workers from it exactly as E2-9 built. The fork machinery stays; it is now the warm path rather than the default. **(3)** The template’s memory-image write comes off the team-up critical path entirely: on a cache miss the template is built *after* the team is up, in the background, under the team’s own context. **(4)** The cache is bounded at **2 GiB**, evicted least-recently-used before a new template is stored, and the bound is stated in `docs/teams.md` and printed when it evicts. **(5)** Acceptance step 1 is re-measured on the reference and **both** numbers reported — cold-path team-up, which is the binding one, and warm-path. The recorded 1098 ms is never rewritten; the new measurement is appended with its CI run id. F-D19’s parking-lot item, E2-5’s budgeted spawns using the fork path, stays parked.

**Evidence:** John’s words: F-D19 was ruled against nested-virt numbers, the bare-KVM measurement says concurrent cold boots win the cold-start case, and data wins. That is the whole of it, and it is the outcome the ruling asked for when it said to measure and report rather than restate. What the data actually shows is that the two costs scale in opposite directions, so neither path is right everywhere: a cold boot is CPU and device setup and the reference runner does it in 109 ms, while a fork is one memory-image write plus N cheap restores and that runner writes 384 MiB in 927 ms. The dev machine reverses both numbers. A strategy that picks one and keeps it is wrong on one of the two machines; a strategy that pays the write once and then forks is right on both, because after the first payment the warm path is 57–61 ms per worker on the reference and ~430 ms on the dev host, and in each case cheaper than that machine’s cold boot. Cold-first is what makes the first run fast; the cache is what makes the second run faster still. Three design choices this leaves to be made and therefore records. The key is a digest over the things actually baked into a memory image — architecture, flavor, the kernel and rootfs sha256 from `image.json`, vCPUs, memory, scratch, the I/O rates, and whether the agent has a spawn budget — so an image rebuild changes the key and a stale template can never be served for a new image, which is the invalidation question F-D25 said had to be answered before any of this was built. The build happens after the team is up rather than on first fork demand, because with cold-first there *is* no fork demand on a miss: waiting for one would mean the cache never fills. And a template is written to a temporary directory and renamed into place, so a half-written image is never a cache hit and two concurrent team-ups cannot serve each other a partial one.

## F-D36

*2026-08-23*

**Plugin tools are namespaced `<plugin>_<tool>`, not `<plugin>.<tool>`.** E4-0’s own text and F-D5’s principle (2) both say a dot. The dot is **legal** and is still not taken, and the reason is downstream of MCP rather than in it. *What was checked.* The MCP specification’s tool-name guidance, added in revision 2025-11-25, says a name SHOULD use ASCII letters, digits, underscore, hyphen *and dot*, and offers `admin.tools.list` as an example of a good one. Both official SDKs accept a dot and only warn. So nothing in MCP forbids it. *What forbids it is everything a tool name passes through afterwards.* The Anthropic Messages API constrains a tool name to `^[a-zA-Z0-9_-]{1,64}$`, which excludes the dot outright, and Claude Code — the first client this project names — rewrites every character outside `A-Za-z0-9_-` to an underscore before the name reaches a model. That rewriting is worse than a rejection would be, because it is silent and it **collides**: `a.b` and `a_b` become the same name. A dotted scheme is therefore not merely mangled but ambiguous after mangling, in the one client the epic exists to serve. *The separator’s own collision is closed rather than hoped away.* `_` would be ambiguous too — plugin `foo_bar` with tool `baz` against plugin `foo` with tool `bar_baz` — so a plugin’s name is constrained to `^[a-z][a-z0-9-]*$`: no underscore, no dot. The prefix cannot contain the separator, so the split is unambiguous by construction. The whole name must also fit 64 characters, the strictest downstream limit, and a plugin whose tool would exceed it is refused at boot rather than advertised and rejected later by somebody else’s API. *One thing the specification says that KelyfOS was going to do anyway.* Its aggregation note — new in the 2026-07-28 revision — says a server’s self-reported name is not guaranteed unique and SHOULD NOT be relied on for disambiguation. So the prefix is the name **declared in kelyfos.toml**, never the one the plugin announces at initialize. That is F-D24’s rule arriving from outside: the host decides what a thing is called, and the thing being named does not get a vote.

## F-D47

*2026-08-23*

**Whatever a caller asked a tool for must be reachable from `structuredContent` alone.** *Source: the live client half of E4-8*, run by John in a signed-in Claude Code session on macOS. *The defect.* `read_file` put the file’s bytes in the text block and only `{path, bytes}` in `structuredContent`. ## F-D54

*2026-08-23*

**The run history is the session records read back, and never a second index.** E5-6 asked for `kelyfos runs` and `rerun`. The obvious implementation is a small database written as each run starts and finishes — a JSON file, or SQLite, keyed by session. *Alternatives.* An index file, which is fast to list and is a second record that can disagree with the first; an index rebuilt lazily when it looks stale, which is the same thing plus a staleness heuristic; or no history at all, leaving `kelyfos log --list`, which cannot say what a run did or what it exited with. *Chosen.* Read the records. One pass per session file, taking only `session.start` and `session.end`, so a session with a hundred thousand events costs what a short one does. The acceptance states the property as a count — one row per session directory, no more and no fewer — which an index would fail the first time somebody deleted a record by hand. **Two things had to be recorded that were not.** `session.start` now carries `cwd`, because `argv` alone does not reproduce a run: `--workspace .` is relative and the policy file is found by walking up from wherever the command was typed. `session.end` now carries `code`, after the OOM adjustment, so the listing shows what the shell saw rather than what the command returned before KelyfOS had its say. Both are existing `Event` fields, so no hash order changed. **And the policy is frozen per run**, a few kilobytes beside the record, for the reason the paused-session freeze exists (docs/qol.md §1.2): a rerun that re-read whatever `kelyfos.toml` says now would reproduce the command and not the run, silently. ## F-D55

*2026-08-23*

**The guest's loopback interface is brought up at boot, always — found by the E5 exit, fixed before the tag.** *What was wrong.* A sandbox with no `--allow` has no NIC and no kernel `ip=` argument, and the kernel leaves `lo` DOWN. Nothing inside such a machine could bind or reach `127.0.0.1`. E5-5's own acceptance did not catch it because every sandbox in it was booted with `--allow example.com`; the epic acceptance used a bare one, which is the commonest kind, and `-p 8080:80` found nothing listening because nothing could listen. *Why it matters more than the symptom.* The whole argument for F-D7 is that a forward is not a network feature — the transport is vsock and the guest dials itself. A version of that which requires a network interface to work is the argument refuting itself. *Alternatives.* Have the host pass an `ip=127.0.0.1` argument, which is a network configuration for a machine that has no network and would read as one; or bring `lo` up lazily when the first forward arrives, which leaves every other reason to want loopback unserved and makes the behaviour depend on a flag. *Chosen.* The supervisor brings `lo` up unconditionally before it announces readiness, `SIOCGIFFLAGS` then `SIOCSIFFLAGS` through `golang.org/x/sys/unix`, which was already a dependency — reading the flags first rather than assuming them, so nothing the kernel already set is cleared. No packet on `lo` can leave the machine by definition, so this grants nothing that the sandbox boundary was holding back. *The lesson for the acceptances* is the one this project keeps relearning in new clothes: a feature tested only in the configuration it was developed in is tested in one configuration. The check now runs against a sandbox with no network, which is where it should have run first.
