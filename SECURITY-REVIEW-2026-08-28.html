Revision note

The seven original findings all hold at 6e55190. Two of them carried a wrong detail (F3), one missed a call site (F7), and one over-stated how consistently a defence is applied (F1); each is corrected in place under a Verification block. The scope card counted 3,457 stale worktree copies under .claude/; the project is 283 Go files.

Fourteen findings were added, F8–F21. Two are High, and both sit in areas the first pass had marked sound: the guest confinement can be stepped around with two commands, and the egress proxy — with the operator’s credentials attached — is reachable by any process on the host. Every added finding now carries a fix written to close the hole rather than narrow it.

What this is

KelyfOS runs untrusted AI-agent workloads inside Firecracker microVMs. Its security rests on five boundaries: the hypervisor and jailer, an egress proxy that is the only route to the network, a seccomp/Landlock profile inside the guest, a policy file that acts as a ceiling no tool call can raise, and a hash-chained flight recorder that is meant to be trustworthy evidence.

The code is unusually well defended — most of the classic failures in this shape of system are not just absent but explicitly reasoned about in comments, with the finding that prompted each fix named. That is also what made the first pass too generous: a well-argued comment reads like a guarantee, and in four places the code under it does not deliver what the comment promises. The verification pass read the code under every “sound” entry a second time, adversarially, and F8–F21 are what came out.

The shape the original noted still holds and now has more examples: most of what is wrong here is a defence implemented correctly on one surface and not carried to the next — view.go to the shim, extract.go’s os.Root to the supervisor’s file tools, the first-request header budget to the terminated leg, the raw-line digest to erase.

F1

Guest text sanitiser misses Unicode format characters

Medium

internal/proto/proto.go:632 SafeText · internal/report/safe.go:59 isDangerousControl

SafeText exists, in its own words, because “a control character in one of those is not a display nuisance — it is the guest deciding what the host’s output looks like.” Its test is ASCII-only:

func SafeText(s string) string {
	for _, r := range s {
		if r < 0x20 || r == 0x7f {
			return strconv.Quote(s)
		}
	}
	return s
}

Unicode format characters (category Cf) sail through. The relevant ones are the bidirectional overrides and isolates — U+202E, U+2066–U+2069 — the Trojan Source class. They reorder how a line renders without changing a byte of its logical content, in a terminal and in a browser alike. The guest gets to choose how its own audit record reads to a person: a domain in an egress blocked line, a path, a store key, a command.

The HTML report is affected the same way and arguably worse, because it is the artefact meant to be read by someone who was not there. internal/report/safe.go routes every guest-influenced value through safe (which is SafeText) or safeBody, and safeBody keys on the same ASCII-only predicate. html/template escapes < > & ' " and nothing else.

Verification

Confirmed. Nothing in the repository references IsPrint, 202e or bidi. One sentence of the original was wrong: SafeText is not “applied consistently and in one place.” Several paths print guest strings raw — that is now its own finding, F20, because fixing the predicate here does nothing for a field that never reaches it.

Secure fix
  • Widen the trigger, keep the escape. strconv.Quote already renders U+202E as ‮; it only needs to be called: 
    func SafeText(s string) string {
	for _, r := range s {
		if r < 0x20 || r == 0x7f || !unicode.IsPrint(r) {
			return strconv.Quote(s)
		}
	}
	return s
}
    unicode.IsPrint also rejects zero-width joiners, soft hyphens and every space other than U+0020 — all of which are invisible and all of which a guest can use to make two different strings read identically. That is the right side to err on for an identity-like field.
  • Give isDangerousControl the same clause so safeBody replaces a bidi character with U+FFFD the way it already replaces a stray ESC. Command output legitimately contains non-ASCII; it does not legitimately contain direction overrides.
  • Add hostile-corpus cases in both packages with "‮elbatpecca" as a store key, a command and a body; the existing corpora test ASCII control bytes only.
  • Close the paths that bypass the function altogether — see F20. A sanitiser is only as good as its coverage.
F2

E2B shim HTTP API has no cross-site request defence

Medium

shim/shim.go:148 Handler · :168 authenticated · :211 createSandbox · host/shim.go:24 --addr

kelyfos shim serves an E2B-compatible REST API on 127.0.0.1:3000. Authentication is opt-in via KELYFOS_SHIM_TOKEN and off by default. What that stance does not account for is the browser: localhost plus no auth is the exact configuration a web page can reach.

The middleware chain is logging(authenticated(mux)). There is no Origin check, no Sec-Fetch-Site check, no Host check, and no CSRF token. Two routes are reachable cross-origin without a preflight:

// POST /files — multipart/form-data is a CORS-"simple" request.
<form method="POST" enctype="multipart/form-data"
      action="http://127.0.0.1:3000/files?path=/work/.git/hooks/pre-commit">

// POST /sandboxes — the body is not required to parse at all.
func (s *Server) createSandbox(w http.ResponseWriter, r *http.Request) {
	var req struct{ TemplateID string `json:"templateID"` }
	_ = json.NewDecoder(r.Body).Decode(&req)  // error discarded
	…
}

So any page the developer visits while the shim is running can write arbitrary files into the live sandbox and boot microVMs up to MaxSandboxes (16). The responses are not readable cross-origin — but the writes land, and a planted file the agent will read is the better outcome for an attacker anyway. DELETE /sandboxes/{id} requires a preflight and is not reachable this way.

Verification

Confirmed. docs/threat-model.md:375 states the residual as “any process on that machine” and never names a web page, so this is a gap in the threat model as well as the code. Also worth stating: --addr accepts any address, and a shim bound off loopback with no token is reachable from the LAN — docs/e2b-shim.md says so, but the code lets it happen silently.

Secure fix
  • Make the browser structurally unable to reach it, in authenticated, before the token check: 
    if site := r.Header.Get("Sec-Fetch-Site"); site != "" && site != "same-origin" && site != "none" {
	writeErr(w, http.StatusForbidden, "cross-site request refused"); return
}
if o := r.Header.Get("Origin"); o != "" {
	writeErr(w, http.StatusForbidden, "browser origins are not clients of this shim"); return
}
if r.Host != s.boundHost { // the literal net.Listener address, as view.go does
	writeErr(w, http.StatusForbidden, "host mismatch"); return
}
    No SDK sends Origin or Sec-Fetch-Site; every browser does. Refusing the presence of Origin outright, rather than allowlisting one, is right because the shim has no legitimate browser client.
  • Flip the default the way view.go does: if KELYFOS_SHIM_TOKEN is unset, mint a 256-bit token at start and print it once with the export line; require --insecure-no-token to run without one. An opt-out is a choice the operator can see; an opt-in is a step nobody takes.
  • Refuse to start on a non-loopback --addr unless a token is set — a bind is the one moment the process knows it is about to be reachable.
  • Stop discarding the decode error in createSandbox: a body that is not JSON should get a 400, not a microVM.
F3

Guest vsock listener never checks the peer CID

Low · latent

internal/vsock/vsock.go:65,101 Listen / Accept · image/buildroot/kernel/kelyfos.fragment · image/check-kernel.sh:21

The supervisor binds its host-facing channels — exec, MCP, control, shell, forward — on VMADDR_CID_ANY. Accept reads the peer’s CID into a remote address and then never looks at it. Any peer that can reach the socket is treated as the host.

Today nothing inside the guest can be that peer, because CONFIG_VSOCKETS_LOOPBACK is off in both base configs. The guest seccomp policy is a denylist and socket is not on it, so a confined process could create an AF_VSOCK socket if the transport existed.

image/buildroot/kernel/base-x86_64.config — the full config buildroot starts from
# CONFIG_VSOCKETS_LOOPBACK is not set    ← a choice: upstream Kconfig says `default y`

image/buildroot/kernel/kelyfos.fragment — the only file check-config.sh verifies
# CONFIG_VHOST_VSOCK is not set          ← pinned, and verified
                                          CONFIG_VSOCKETS_LOOPBACK: absent
Verification

Premise confirmed; two details corrected. First, the original called the disabled loopback transport “upstream default, not a choice”. It is the opposite: net/vmw_vsock/Kconfig gives VSOCKETS_LOOPBACK default y, so the base config disables it against the default, and a regenerated config or an olddefconfig over a kernel bump would pull it back on. That makes pinning it in the fragment more important, not less, because check-kernel.sh concatenates only the two fragments into what check-config.sh verifies.

Second, the stated impact — “unrestricted filesystem access, bypassing the profile” — is wrong. supervisor/writable.go (P6-24) deliberately bounds the PID-1 file tools to the same writable trees the profile grants a confined child. A guest process that reached PortMCP would gain the supervisor’s other tools and the control channel, which is still worth refusing, but not the filesystem. Low stands.

Secure fix
  • In Accept, refuse a peer that is not the host, and say so on the supervisor log so a future loopback regression is visible rather than silent: 
    if vm, ok := sa.(*unix.SockaddrVM); ok {
	if vm.CID != unix.VMADDR_CID_HOST {
		unix.Close(nfd)
		logf("vsock: refused a connection from CID %d on port %d", vm.CID, l.addr.Port)
		continue // keep accepting
	}
	remote = &Addr{CID: vm.CID, Port: vm.Port}
}
  • Add # CONFIG_VSOCKETS_LOOPBACK is not set to kelyfos.fragment beside the VHOST_VSOCK line, with a comment naming this finding, so the build fails the day it flips.

Workspace contents lost for a directory name ending in whitespace

Low

internal/sandbox/extract.go:131–165 listDirs · :103 listImage

listDirs batches directories into one debugfs script and attributes each block of records to the directory named on the echoed command line:

// building the script — the directory is NOT quoted
fmt.Fprintf(&script, "ls -l -p %s\n", d)

// attributing the output
if rest, ok := strings.CutPrefix(line, "debugfs: ls -l -p "); ok {
	current = strings.TrimSpace(rest)
	continue
}
blocks[current] = append(blocks[current], line)

validName refuses /, NUL, ., .., quotes and control characters — but not spaces. A directory named "notes " produces dir == "/notes " and current == "/notes". The keys do not match, blocks[dir] is empty, and the directory is created on the host with none of its contents and no error anywhere. Interior spaces are a second problem: the script line is whitespace-delimited.

Verification

Confirmed as written. Still to be reproduced with a real image; no toolchain was available on either pass.

Secure fix
  • Quote the directory as dumpFiles already quotes file paths — ls -l -p "%s" — and match the echo with the quotes on, so the key is the string that was submitted, not a trimmed guess: 
    fmt.Fprintf(&script, "ls -l -p \"%s\"\n", d)
…
if rest, ok := strings.CutPrefix(line, `debugfs: ls -l -p "`); ok {
	current = strings.TrimSuffix(rest, `"`)
	continue
}
    validName already refuses both quote characters, so the quoting cannot be broken from inside the name.
  • Cross-check the attribution: after the loop, any directory in dirs with no block at all is an error (debugfs echoes every command, so a missing echo means the parse drifted). A workspace missing a directory without saying so is the failure mode this package refuses everywhere else.
  • Add "notes " and "my notes" to the extraction corpus.

MCP client config files created world-readable

Low

host/connect.go:222,225,254 writeTo / removeFrom · host/connect_clients.go:47,76

os.MkdirAll(filepath.Dir(path), 0o755)
os.WriteFile(path, updated, 0o644)

Two of the targets live under $HOME and are files that commonly grow credentials later: ~/.codex/config.toml and ~/.gemini/settings.json. os.WriteFile only applies perm on creation, so the exposure is the case where KelyfOS is the first thing to create the file — the common case for a fresh setup — and the client that later writes an API key into it will keep the mode it found.

Verification

Confirmed. Target paths confirmed in connect_clients.go. Two other 0o644 writes exist (lima_darwin.go, the cgroup cpu.max write) and are harmless.

Secure fix
  • 0o600 / 0o700 for anything whose path is under the user’s home; project-local files (.mcp.json, .cursor/mcp.json) keep 0o644 because they are meant to be committed. Decide by prefix, not by client name, so a client added later inherits the rule.
  • Write to a sibling temp file with os.CreateTemp in the same directory, fsync, then os.Rename over the target — the pattern host/log.go already uses. This is a read-modify-write of a file another program may be editing, and a rename is the only atomic replacement available.
  • Never lower an existing file’s mode: Stat first and keep the stricter of the two.
F6

Erase silently drops chain fields an older build cannot parse

Informational

internal/recorder/erase.go:76 Erase · internal/recorder/recorder.go:1056 digestOfLine · :1073 Read

Verify recomputes a digest from the raw line rather than the parsed struct, precisely so that an older build reading a newer chain does not report a legitimate record as modified. Erase does not inherit the property: it goes Read → redactEventFields → hashOf → re-marshal, and Read is json.Unmarshal into Event. A field this binary’s struct does not carry is gone from the rewritten file, the chain still verifies, and session.erasure’s Modified count does not reflect it.

Verification

Confirmed. erase.go never compares an event’s v against Version; it only stamps its own erasure event with it.

Secure fix
  • Refuse first, then get it right. Before any rewrite: if e.V > Version { return fmt.Errorf("event %d was written by a newer kelyfos (v%d); upgrade before erasing", e.Seq, e.V) }. This is one line and makes the skew impossible to hit silently.
  • Then make the rewrite lossless: redact at the raw-JSON level by unmarshalling each line into map[string]json.RawMessage, replacing only the keys the exemption map names as redactable, and re-marshalling the map. Unknown members survive, which is the guarantee digestOfLine already makes for reads. Key order changes, but the digest is recomputed anyway.
  • Count fields, not events, in a second counter alongside Modified, so an auditor can compare it against what a redaction should have touched.

Snapshot names validated on the MCP path, not the CLI path

Informational

host/servemcpstate.go:35 validSnapshotName · host/snapshot.go:41 snapshotDir · :59,111 · host/fork.go:77,166 · host/bench.go:152

validSnapshotName is a good check — an explicit character allowlist, a length bound, and a leading-dot refusal — and every MCP tool calls it before reaching snapshotDir. The CLI call sites do not. Both paths are driven by the local user’s own flags, so no privilege boundary is crossed; it is worth closing because a rule enforced at some call sites is a rule the next call site will miss.

Verification

Confirmed, and the original under-counted: there are five unvalidated callers, not four — host/bench.go:152 (oneRestore) also passes a raw name straight to snapshotDir. Which is the finding’s own point, demonstrated.

Secure fix
  • Make the path function the gate: 
    func snapshotDir(name string) (string, error) {
	if err := validSnapshotName(name); err != nil {
		return "", err
	}
	return filepath.Join(sandbox.Root(), "snapshots", name), nil
}
    The compiler then finds every caller for you, including the one the review missed.
  • Belt and braces: after joining, assert filepath.Rel(root, dir) has no .. component. It cannot happen once the name is validated, but the assertion is what makes the next refactor safe.

F8

Any binary named kelyfos-confine runs unconfined as root

High

supervisor/confine.go:104 confine · :115 confineHelperMarker · supervisor/reaper.go:80 the single call site · supervisor/exec.go:111 exec.Command(argv[0], …)

confine is the one choke point that wraps every spawned command in the re-exec’d --confine helper, which applies Landlock and seccomp and then execves the real program. It is placed in startAndRegister so that no caller can forget it — the comment says so, and it is the right design. The guard inside it is not:

func confine(cmd *exec.Cmd) {
	if guestProfile == nil || cmd.Err != nil || cmd.Path == "" {
		return
	}
	if strings.HasSuffix(cmd.Path, confineHelperMarker) {
		return // already wrapped; nothing wraps twice
	}
	real, argv := cmd.Path, append([]string{}, cmd.Args...)
	cmd.Path = "/proc/self/exe"
	cmd.Args = append([]string{confineHelperMarker, confineFlag, guestProfile.Name, "--path", real, "--"}, argv...)
}

cmd.Path is the target program’s path — the agent’s argv[0], resolved. A command this function has already wrapped has Path == "/proc/self/exe", which never ends in the marker, so the guard never fires for the case it was written for. It fires for exactly one other case: a program the agent chose to name kelyfos-confine. Then the function returns without wrapping, and cmd.Start() runs it as PID 1’s child — root, no Landlock ruleset, no seccomp filter.

# from any confined exec — /root is writable and executable under the profile
cp /bin/sh /root/kelyfos-confine
# next exec: argv[0] carries a separator, so exec.Command uses it verbatim
exec argv=["/root/kelyfos-confine", "-c", "mount -o remount,rw / ; cat /dev/vdb > /root/disk ; …"]

Everything the profile exists to deny — mount, ptrace, reboot, raw access to /dev/vda and /dev/vdb, editing the toolbox — is available to that process. docs/threat-model.md:266 promises that “every process the supervisor spawns … is confined”; this is the two-command counter-example. No test exercises confine().

Secure fix
  1. Delete the guard. confine has one caller, startAndRegister, and nothing constructs an already-wrapped exec.Cmd. A check that protects against a call that cannot happen is only ever a hole.
  2. If a re-entrancy guard is genuinely wanted for the future, key it on something the agent cannot choose — a private marker on the command, not a property of the target: 
    type confinedCmd struct{ *exec.Cmd; wrapped bool }
// or, minimally, on the wrapper's own identity:
if cmd.Path == "/proc/self/exe" && len(cmd.Args) > 0 && cmd.Args[0] == confineHelperMarker {
	return
}
  3. Fail closed at the call site. After confine(cmd) in startAndRegister, assert the invariant and refuse to start otherwise: if guestProfile != nil && cmd.Path != "/proc/self/exe" { return errNotConfined }. The supervisor already refuses to report ready on an unenforced profile; it should refuse to spawn on one too.
  4. Test it: a hostile-corpus case that spawns /root/kelyfos-confine and asserts, from inside the child, that landlock_restrict_self has been applied (open /usr/bin for write and expect EACCES) and that mount(2) returns EPERM. Name the test after this finding.
F9

Egress proxy is reachable by any local process, credentials included

High

internal/egress/proxy.go:251 Listen · internal/sandbox/network.go:190–200 applyFirewall · internal/egress/terminate.go:98 credential attach

The proxy binds the host’s own TAP address, and the comment above it draws the conclusion that makes this finding:

// Listen binds the proxy. The address is the host's TAP address, so the proxy
// is reachable from exactly one sandbox and from nothing else on the machine.
func (p *Proxy) Listen(addr string) (int, error) {
	ln, err := net.Listen("tcp", addr)      // addr = 169.254.x.1:0

An address on the TAP is still a local address of the host. A connection from a local process to 169.254.x.1:port never touches the TAP; the kernel routes it over lo, and the firewall has no opinion about it:

chain input {
	type filter hook input priority filter; policy accept;
	iifname "tap-xxxx" jump kelyfos_guest_in   // only packets FROM the guest are inspected
}

Nothing in handle looks at RemoteAddr. So any process on the host — another user on a shared box, a CI job, a compromised npm script in the developer’s shell — can ss -ltn, find the port, and send CONNECT api.github.com:443. The proxy terminates TLS and attaches GITHUB_TOKEN from the operator’s environment exactly as it would for the sandbox, then records the traffic in the flight recorder as the sandbox’s own. The credential never leaves the host, which is the property secret.go defends; it is simply spent by someone who cannot read the environment it lives in.

The same door also lets a local process consume all 128 connection slots with idle tunnels, and use the host’s allowlisted egress under the sandbox’s name. Unconfirmed extension: with the Linux default arp_ignore=0, the host answers ARP for 169.254.x.1 on any interface, which would open the port to the physical segment as well.

docs/threat-model.md states “loopback is shared with every local user” as the residual for the shim and for kelyfos view. It does not state it for the proxy — the one listener that carries credentials — and the first pass, reading the comment rather than the ruleset, marked credential injection sound.

Secure fix
  1. Check the peer in the proxy, so the property does not depend on the firewall being right. Give Proxy a Peer netip.Addr set from Network.GuestIP, and refuse anything else at the top of handle: 
    ra, ok := conn.RemoteAddr().(*net.TCPAddr)
peer, _ := netip.AddrFromSlice(ra.IP)
if !ok || peer.Unmap() != p.Peer {          // p.Peer is the guest's TAP address
	p.report(Attempt{Reason: ReasonForeignPeer, Host: conn.RemoteAddr().String()})
	conn.Close()
	return
}
    Record the refusal: a foreign connection to this port is an event the operator should see in the log.
  2. Close it in the ruleset too, in the input chain, so the port is unreachable even if a future proxy forgets step 1: 
    chain input {
	type filter hook input priority filter; policy accept;
	ip daddr %[3]s iifname != "%[2]s" counter drop   // HostIP only from the TAP
	iifname "%[2]s" jump kelyfos_guest_in
}
    Packets from local processes to HostIP arrive with iifname "lo" and are dropped; the guest’s arrive on the TAP and proceed as before. dev/accept-forward.sh’s ruleset diff should carry the new line.
  3. The LAN case needs nothing extra once step 2 is in: a packet that arrives on the physical NIC for HostIP has iifname != tap and is dropped by the same line. Setting arp_ignore system-wide would be broader than this product should reach.
  4. Write the residual into docs/threat-model.md under the proxy, in the same words the shim and viewer entries use, and add a test to network_test.go that dials HostIP:port from the host and expects a refusal.
F10

A confined process can mknod its way to the raw disks

Medium

supervisor/profile.go:67 writableEverywhere · :130–135 writeRights · supervisor/mount.go:73 overlay flags · supervisor/profile_policy.go no mknod

profile.go names the two raw block devices, /dev/vda and /dev/vdb, as the reason /dev is not granted wholesale, and says the disks are withheld “from every process this supervisor starts.” Three facts together make that untrue for a process that is root, which every confined process is:

// profile.go — the rights granted on every writable tree, /root included
const writeRights = … |
	unix.LANDLOCK_ACCESS_FS_MAKE_CHAR |
	unix.LANDLOCK_ACCESS_FS_MAKE_BLOCK |
	…

// mount.go:73 — the merged root, where /root lives
unix.Mount("overlay", "/mnt/merged", "overlay", 0, …)   // no MS_NODEV, no MS_NOSUID

// profile_policy.go — mknod, mknodat: not on the list

So: read the major:minor of vdb from /proc/partitions, mknod /root/disk b 254 16, and the workspace block device — attached read-write — is open for raw reads and writes, past the nosuid,nodev mount that guards /work. /dev/vda is readable the same way. The immediate consequence is narrow (the workspace is the agent’s own, the root image is not secret), but raw writes let the guest hand the host’s debugfs an arbitrarily malformed ext4, and the written guarantee is false.

Secure fix
  • Remove MAKE_CHAR and MAKE_BLOCK from writeRights. No build tool, package manager or test runner creates device nodes; MAKE_FIFO and MAKE_SOCK are the ones programs need and they stay. Landlock refuses the mknod with EACCES regardless of what seccomp does.
  • Mount the merged overlay with MS_NODEV|MS_NOSUID at mount.go:73. /dev is a separate devtmpfs, so nothing on the root needs device semantics; this makes a node that somehow got created inert. Do not also add mknod/mknodat to the seccomp refusal list: mkfifo(3) is mknodat with S_IFIFO, and a number-only filter would break every tool that uses a named pipe.
  • Test both layers: from a confined child, mknod a block node under /root and expect EACCES; then, with the Landlock rule temporarily loosened in the test, create one and expect open on it to fail with EACCES because of nodev.
F11

write_file re-checks for symlinks but still opens through one

Medium

supervisor/writable.go:96 noSymlinksBeneath · supervisor/tools.go:413–421 the write

The supervisor’s file tools run in PID 1, which is not confined, so writableFor checks that a path is inside a writable tree and that no component is a symlink. The comment on the second check is candid about why it exists: “a symlink can be planted in the gap between that decision and this call.” But the second check is the same lexical Lstat walk as the first, and the write that follows it is an ordinary os.WriteFile:

A confined exec holds MAKE_SYM on /work. Secure fix

  • Keep noSymlinksBeneath only for the error message; it is no longer the thing that makes the write safe.
  • Test the race: a goroutine flipping a symlink under a path while the tool writes it a few thousand times, asserting that the target file is never touched.

Order of work

If the fixes are taken in sequence, this is the sequence. Each step is independent of the next; the order is by what an attacker would reach first.

  1. F8 — delete the guard in confine; add the fail-closed assertion and the test. Half a day, and the guest profile means what the docs say again.
  2. F9 — peer check in handle and the iifname != tap drop line. Same day. Then write the residual into the threat model.
  3. F10 and F11 — two rights out of writeRights, MS_NODEV|MS_NOSUID on the overlay, and os.Root in the file tools. These close the guest-side profile properly.
  4. F13 and F12 — the recorder fails closed and erase covers what it says. These are the product’s promise.
  5. F14, F15, F16 — three small changes in internal/egress, one afternoon together.
  6. F17, F18, F19 — host-side integrity; each is a few lines plus a corpus case.
  7. F20, F1 — sanitise at the edge, then widen the predicate; doing them in that order means the predicate change lands everywhere at once.
  8. F2, F21 — the two that change defaults, which want a line in the changelog and a decision from whoever owns the product.
  9. F3–F7 — as written; none is urgent, all are small.

Limits of this review

  • Static only, both passes. No Go toolchain was available, so nothing was compiled, no test ran, and no exploit was executed. F8 and F9 are derived from unambiguous code paths and are stated with confidence; F11’s race, F17’s ENOSPC path and F4’s debugfs interaction are predicted and should be reproduced before being closed.
  • Independence was partial on the second pass. The first pass read no project documents. The verification pass read docs/threat-model.md, docs/e2b-shim.md, docs/view.md and the kernel Kconfig upstream, to check whether any finding was already an accepted residual. F2, F9 and F13 are not; the kernel-surface items in “Also noted” are, and are listed as such.
  • Depth was uneven. Every F-numbered finding was re-read in source by the author. The “Also noted” items were confirmed by the reviewing agents but not independently re-derived, and are held at Low or Info for that reason as much as for impact.
  • Out of scope by construction. Hypervisor escape, guest kernel vulnerabilities as such (as opposed to the guest kernel’s configuration), and the supply chain of the three direct Go dependencies were not assessed. The Firecracker and jailer configuration was assessed from how KelyfOS invokes it.
